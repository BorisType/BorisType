# Диагностика HTTP mapping в WebSoft HCM

Наблюдения получены на одной Linux web-ноде HCM 2025.2.1333 с .NET 9. Для сравнения запросов в кластере сначала установи, какая нода и какой экземпляр обработчика ответили.

**Откуда берётся 401 после успешного SOAP-входа.** На стенде со схемой аутентификации хоста `None` вход SDK через `/spxml_web/main.htm` вернул 200 и `SessionID`. Диагностический маршрут Kestrel с этой сессией вернул 401 даже после успешного SOAP-вызова. Вход той же учёткой через портал `GET /home` выдал `x-auth-id`. С этой cookie диагностический маршрут и штатный `/$hcm/checkmessages` вернули 200. Следующий независимый запрос без cookie снова получил 401. Для диагностики сравни способ входа, HTTP-статус и совпадение пользователя в защищённом обработчике. Значения cookie и claims оставь вне журналов. Доступность портального входа зависит от настройки стенда.

`HttpContext.User` показывает пользователя ASP.NET. Для операции над документом проверь права LDS и автора сохранённого изменения отдельно, под учётками с разными правами. На этом стенде через диагностический маршрут проверяли вход пользователя.

**Почему после обновления отвечает прежняя DLL.** На проверенной установке HCM обнаружил компонент и зарегистрировал его `IDatexHttpMapping` при старте web-процесса. Сразу после первой установки маршрут ещё возвращал 404. При обновлении работающий обработчик продолжал отвечать V1 до рестарта. Для диагностики сравни выбранную на диске версию с MVID сборки, которая обслужила HTTP-запрос. MVID — идентификатор модуля из метаданных .NET.

В опыте две DLL с одинаковым именем сборки лежали в разных каталогах. После рестарта указатель содержал V2, но `GetAssembly` даже с полным путём к V2 загрузил V1. Это подтвердили путь в журнале `dotnetcore` и MVID в ответе маршрута. Когда релизы собрали с разными `AssemblyName` и обработчик проверил свой MVID перед регистрацией, после рестарта ответила V2. Для каждого релиза меняли имя в метаданных сборки и сохраняли предыдущую DLL на диске. Правки общего `xhttp_config.json` в этом опыте не потребовались.

Проверка блокировки открытой DLL на Windows проводилась в managed CI. Для Windows HCM и других версий платформы требуется собственная проверка.
