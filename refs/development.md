# Разработка и ведение знаний

## Что где хранить

| Содержание                                                           | Место и причина                                                                 |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Как установить и использовать инструмент, публичный контракт         | `docs/`; пользователь получает законченный сценарий                             |
| Почему выбран подход, чем подтверждён, какие альтернативы не подошли | Тематическая запись в `refs/`                                                   |
| Результат конкретного исследования                                   | `refs/research/` вместе с пробами, результатами и prerequisites                 |
| Значимое решение                                                     | `refs/decisions/` или раздел тематической записи; отдельная ADR нужна по смыслу |
| Конкретный долг и остающиеся проверки                                | Корневой `TODO.md`; при наличии issue — ссылка вместо копии статуса             |
| Быстрый вход в отдельный пакет                                       | README пакета, доступный и после установки без checkout                         |
| Порядок действий агента                                              | Skill с узкой областью применения; внутренний skill может требовать checkout    |

Внутренние знания группируются по вопросу, а не по номеру сессии. Запись должна
позволять найти проблему, причину выбора, существенные альтернативы, основания,
границы применимости и условия пересмотра. Фиксированный набор заголовков не требуется.
Список всех файлов не заменяет такое объяснение; для навигации достаточно точек входа.

## Текущие настройки и проверки

Node и pnpm выбираются из [.node-version](../.node-version) и
[package.json](../package.json), .NET SDK — из [global.json](../global.json).
Версии зависимостей определяются manifests и lockfiles. TypeScript Compiler API
пока остаётся на линии 6: переход на другой API не является обычным обновлением CLI.

Из корня checkout:

```sh
pnpm install --frozen-lockfile
pnpm exec turbo run build
pnpm lint
pnpm format:check
pnpm docs:test
pnpm docs:check
pnpm docs:build
```

Выбирай проверки по затронутому поведению. Сборка сайта проверяет рендеринг,
`docs:check` — локальные цели ссылок, навигацию и комплектность переноса, но не
семантическую истинность текста, внешние URL или все anchors.
`docs:test` проверяет checker на временных fixtures. Для coverage переноса нужна
история baseline из карты (в shallow checkout: `git fetch --unshallow`).
Файл [link-exceptions.json](link-exceptions.json) оставлен как явный реестр
исключений; после миграции он пуст. Исполняемые примеры требуют относящихся к ним
проверок; перенос Markdown не требует нового native запуска известной crash-пробы.
Проверки компилятора описаны [отдельно](compiler/verification.md).
MCP и .NET имеют свои локальные suites и отдельные native runners в package scripts.
Нативные runners не запускаются автоматически ради документационного изменения.

## Изменения и смысловая дельта

Для содержательного PR опиши было → стало, причину, основание и последствия
для пользователей/совместимости, если они есть. Различай изменение реализации,
исправление прежнего знания и расширение подтверждений. Новая проверенная ОС
не означает, что код обязательно поменялся.

Обновляй затронутые актуальные документы. Значимое изменение решения или опровержение
прежнего основания сохраняй в `refs/` со ссылкой на прежнее решение и новые данные.
Исторические результаты не переписывай как результаты новой ревизии. Git сохраняет
точный diff, PR — смысл изменения; важное обоснование должно оставаться доступным
и из самого репозитория. Changesets предназначены для release notes пакетов.

Не требуется обновлять ROADMAP при каждом fix, вести `DELTA.md`, писать ADR на
опечатку или документировать очевидный код. Комментарии объясняют контракт и
неочевидные решения; форма зависит от TS/C#/BS и потребителя API.

## Исследование и evidence

Документация Datex может ошибаться и пропускать аргументы. Для подходящих функций
сопоставляй конкретные статьи с [wshcmx/types](https://github.com/wshcmx/types),
указывая revision и файл, и с доступным кодом/наблюдениями. Отсутствие declaration
не доказывает отсутствие API. Declarations не доказывают runtime semantics.

Различай документацию, статическую находку, JS/mock, managed test и запуск C-runtime.
У пробы сохраняются исходник, способ запуска, actual/expected, идентичность кода,
версия/ОС/runtime/carrier, ограничения и результат очистки. Неизвестное явно
обозначается. Если runtime нельзя распространять, воспроизведение требует отдельно
предоставленного экземпляра; один hash этого не заменяет.

Проба может зависать или завершать платформенный процесс. Такие эксперименты
отделяются от обычных регрессий. Timeout клиента не отменяет серверный код.
Сохранение evidence не является инструкцией автоматически повторить эксперимент.

## Планы, суммаризация и архив

Небольшой задаче достаточно рабочего checklist или issue/PR. Длинное исследование
может использовать одну заметку: вопрос, варианты, результаты, что осталось проверить,
следующий шаг и критерий завершения. Отдельный подробный план полезен для зависимой
миграции или передачи работы. Обязательная цепочка spec/plan/tasks/results не нужна.

После завершения актуальное объяснение переносится в тематическую запись. Полезная
история остаётся с датой, статусом и ссылкой на текущий вход. При суммаризации сохраняй
неудачные альтернативы, контрпримеры, ограничения и открытые проблемы. Для удаления
дубля сначала установи отсутствие уникальных полезных сведений. Исполняемые источники,
manifests и результаты переносятся комплектом; исторические bytes не форматируются
попутно с прозой. У перенесённых byte-preserved artifacts
[.gitattributes](../.gitattributes) отключает EOL conversion, чтобы Windows checkout
не менял hashes. Незакрытый finding не исчезает вследствие архивирования.

## Факт и направление изменений

Существующее поведение, принятое требование, желаемое улучшение и гипотеза имеют
разный статус. Например, core CLI пока вызывает `process.exit()`; направление —
возвращать управление вызывающему коду, оставляя завершение процесса CLI.
Новые функции core должны соблюдать эту границу; старые нарушения остаются
[явным долгом](../TODO.md). Документация не утверждает, что миграция уже сделана.

Ограничения BorisScript относятся к платформенному коду и output. Они не запрещают
современные возможности Node TypeScript или C# в других слоях.

## CLI и общие утилиты

CLI wrappers преобразуют параметры и результаты в пользовательские сообщения/exit
codes; core остаётся пригодным для вызова из другого кода. Это направление для
новой логики, со старым долгом, указанным выше. Перед добавлением собственного XML
parser/builder, logger или `.properties` parser проверь существующие
[xml.ts](../packages/bt-cli/src/core/utils/xml.ts),
[logger.ts](../packages/bt-cli/src/core/logger.ts) и
[properties.ts](../packages/bt-cli/src/core/utils/properties.ts): повторная настройка
может менять контракт. В NodeNext TS относительные импорты используют `.js`,
как в исходниках пакетов. Это не ограничение для BS или C# imports.
