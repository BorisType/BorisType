# Поставка и обновление HTTP-транспорта ws-client

Предлагаемый контракт SDK для MCP и CLI. На Linux HCM 2025.2.1333 проверены установка диагностического компонента через evaluator, регистрация первого маршрута при следующем старте web-процесса и загрузка нескольких тестовых backend DLL при работающем mapping. Автоматический установщик HTTP-транспорта в выпущенном SDK отсутствует. [Результаты опытов](../research/dotnet/16-http-mapping-transport.md) · [Действующий установщик FileSystem](managed-runtime.md).

## Что доставляет npm-пакет

| Часть                                                       | Когда вступает в силу                                                                                                                                     |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Компонент WebSoft с собственным кодом и стабильным `init()` | HCM обнаруживает его при старте. Компонент нужен один на установку. В общем `xhttp_config.json` и `source/api_ext.xml` записей не требуется.              |
| Обёртка с `IDatexHttpMapping`                               | `init()` загружает подготовленную для этого запуска сборку и регистрирует постоянный HTTP-префикс. Процесс продолжает использовать эту обёртку до выхода. |
| Backend с реализацией операций                              | Работающая обёртка принимает совместимый проверенный backend и публикует его в своём диспетчере. Новые операции доступны под тем же префиксом сразу.      |

Сборка `@boristype/ws-client` вкладывает в npm-архив готовый компонент, DLL и манифест. У пользователя SDK достаточно Node и настроенного подключения к HCM. Версия npm, версия обёртки, диапазон поддерживаемого ею интерфейса backend и версия протокола клиентских операций имеют разный смысл. Манифест указывает совместимость и идентичность конкретных сборок. Сборке самой обёртки нужны compile-time references целевой платформы. Для сборки и упаковки без локальной установки HCM нужен воспроизводимый источник разрешённых references или отдельно собранный и проверенный release-артефакт. Vendor DLL в клиентский bundle не входят. Если новый MCP использует прежние артефакты, установка ничего не меняет.

## Первое использование

1. Запуск stdio-сервера и `tools/list` остаются локальными. Первый вызов операции, для которой SDK поддерживает HTTP, или явная диагностика транспорта запускает проверку. Если защищённый маршрут подтвердил пользователя и совместимые возможности, операция сразу идёт по HTTP.
2. При отсутствии подтверждённой установки SDK через авторизованный SOAP evaluator проверяет на отвечающей ноде каталог компонента, файлы и состояние процесса. По одному HTTP 404 решение о перезапуске принять нельзя. Готовая совместимая установка доступна пользователю с правами на соответствующую операцию, даже если ему запрещено устанавливать DLL.
3. На чистой установке SDK с правами на запись подготавливает **сразу обёртку и первый backend**. Он доставляет файлы во временный каталог на той же файловой системе вне сканируемых каталогов компонентов, сверяет список, длины, SHA-256 и идентичность DLL. Под блокировкой установщика целиком публикует собственный каталог компонента переименованием в свободное имя. Если конкурент успел первым, SDK перечитывает опубликованный манифест. Существующий чужой каталог, расхождение хеша или отказ в правах дают отдельную причину ошибки.
4. После подтверждения публикации SDK фиксирует в квитанции установки ноду и поколение процесса, если их удалось достоверно установить, и сообщает `restart_required / first_install`. Для операций, у которых уже есть реализация SOAP, клиент может использовать её до следующего запуска web-процесса. Для операции только на HTTP возвращает статус и конкретное действие. При следующем обращении SDK повторяет проверку без перезапуска MCP. Сам клиент HCM не перезапускает.

Выбор транспорта завершается **до отправки операции**. Отказ в авторизации прикладного HTTP-вызова возвращается вызывающему. После обрыва или таймаута записи её исход может быть неизвестен. Отправлять ту же запись через SOAP нельзя.

## Обновление backend без рестарта

Для первого варианта предлагается **одна активная реализация на major протокола**. Два клиента с совместимым протоколом используют одну реализацию. Несовместимые major могут обслуживаться одновременно. Манифест клиента задаёт major, минимальную подходящую версию backend и необходимые операции. Handshake возвращает фактические возможности, версию и build ID. Если активная версия покрывает требования, SDK использует её сразу. Релизу, который требует исправления при прежнем наборе операций, достаточно повысить минимум версии. Старый npm-клиент при подключении не понижает активную версию. Одинаковая версия с разными сборками считается конфликтом. Более новая сборка того же major должна сохранять контракт уже опубликованных операций.

Установщик кладёт новую сборку и зависимости в собственный неизменяемый каталог. Для выпуска нужен проверяемый источник артефактов. Предлагается манифест, подписанный при выпуске, с ключом проверки в обёртке. На каждом стенде отдельно настраивать ключ не требуется. Публичный запрос к операции может выбрать поддерживаемый протокол. Диспетчер не принимает путь, URL или произвольную DLL для исполнения. В прототипе проверялись три заранее известных хеша. Допуск будущих выпусков и смена ключа требуют отдельной проверки.

Работающая обёртка при согласовании версии проверяет совместимость, загружает сборку из опубликованного каталога, проверяет поддерживаемые операции и только затем переключает обработчик. Для первой версии можно повторить проверенный вариант с уникальным CLR simple name на сборку и без конфликтующих частных зависимостей. Одна лишь смена имени файла для side-by-side недостаточна. Параллельные установки сериализуются по компоненту, а публикация обработчика — по major. После таймаута установщик перечитывает состояние на сервере перед повторной попыткой.

Начатый запрос удерживает выбранный обработчик до завершения. Ошибка кандидата оставляет рабочую сборку доступной и видна в диагностике. Для холодного старта хранится последняя проверенная версия каждого major. Сборки в памяти учитываются до остановки процесса. Бесконечную горячую замену без расхода памяти обещать нельзя. Первую прикладную операцию стоит выбрать без состояния между вызовами. Перед переносом upload и операций с `readToken` нужны отдельные проверки незавершённой последовательности при смене backend или ноды.

## Обновление обёртки

Если текущая обёртка поддерживает нужный backend, обновление MCP само по себе не требует рестарта. Если нужного интерфейса нет или обёртку обновляют целенаправленно, SDK заранее доставляет **новую обёртку вместе с подходящим backend**. DLL получает новый каталог и идентичность. После проверки файлов установщик атомарно записывает выбор для следующего запуска. Уже загруженная DLL, старая версия на диске и её рабочие backend остаются доступными. Старый клиент не может откатить выбор для следующего запуска. Автоматическое обновление обёртки допускается, только если новая поддерживает и уже активные major на этом стенде. Вывод из поддержки одного из них потребует отдельного решения оператора.

Стабильный `init()` читает указатель при старте. Формат указателя должен оставаться читаемым всеми поддерживаемыми версиями стартового кода. Если изменился сам входной формат компонента, это отдельная миграция с проверкой остановленной ноды. Замена непустого дерева файлов работающего компонента по одному не даёт атомарности.

`RegisterAspNetMapping(true)` подтверждает включение обработчика в startup. SDK считает транспорт готовым после ответа защищённого маршрута с ожидаемыми обёрткой и возможностями. Обновление, не поднявшее маршрут после рестарта, получает причину `activation_failed` при наличии подтверждения с той же ноды. Для восстановления можно явно выбрать предыдущую рабочую обёртку на следующий запуск. Недоступный стенд или разные ноды за балансировщиком оставляют результат неподтверждённым.

## Что видит агент

Предлагается расширить существующий `wshcm_runtime_status` выбором `component: "http_transport"`. Вызов с пустым объектом сохраняет существующий контракт FileSystem. Для HTTP возвращаются причина, отдельно подготовленная и загруженная версии обёртки, активная версия backend и major, идентичность ответившего web-процесса и требуемое действие. Отдельно сообщается, может ли **конкретная запрошенная операция** продолжить работу на старом backend или через SOAP. Если первая операция уже выполнена через SOAP, при переходе в `restart_required` MCP один раз за сессию добавляет к результату отдельный текстовый блок с причиной и действием. Первый блок содержит обычный результат операции. Диагностика по явному запросу возвращает состояние каждый раз.

| Наблюдение на подтверждённой ноде                                | Сообщение для агента                                                                                                                            |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Компонент впервые опубликован на работающем HCM                  | «HTTP-компонент установлен. Чтобы включить Kestrel, перезапустите web-процесс HCM на этой ноде. Повторная установка и перезапуск MCP не нужны». |
| Загружена обёртка 1, подготовлена 2                              | «Работает обёртка 1. Обёртка 2 подготовлена. Для операций, которым нужна версия 2, требуется перезапуск web-процесса HCM».                      |
| Совместимый backend обновлён                                     | «Backend активен. Перезапуск не требуется».                                                                                                     |
| Нода уже перезапустилась, ожидаемый mapping не инициализировался | «Компонент установлен, активация не подтвердилась после перезапуска. Проверьте инициализацию компонента в журналах этой web-ноды».              |
| Установка запрещена или артефакт повреждён                       | Статус `blocked` с причиной. Повторная команда «перезапустите стенд» здесь не поможет.                                                          |

Для кластера состояние относится к ответившему процессу. Само наличие файлов в общем каталоге не подтверждает регистрацию на всех web-нодах. После пересоздания Docker-контейнера с непостоянным каталогом `components/` установка из SDK снова потребует активации. При поставке компонента в образе он регистрируется уже на первом старте контейнера.

## Первое сквозное подтверждение

- Распаковать опубликованный npm-артефакт на машине без .NET SDK. Проверить первую установку штатным evaluator, параллельную первую установку, диагностику до рестарта и работу после рестарта тем же MCP.
- На одном процессе одновременно подключить старый и новый клиент. Проверить горячее обновление, два major, старый клиент после нового и повреждённого кандидата. Проверить, что начатый запрос завершается на своей сборке.
- Подготовить новую обёртку под нагрузкой. До рестарта проверить работоспособность старой версии и сообщение о подготовленной новой. После рестарта сверить идентичность реально загруженной сборки. При сбое старта проверить диагностику и явное восстановление предыдущей версии.
- Провести одну настоящую операцию чтения под двумя учётными записями с разными правами. Подтвердить отказ для запрещённого объекта и отсутствие повторной отправки после неопределённого исхода. Для балансировщика отдельно проверить переход между нодами с разными версиями.
