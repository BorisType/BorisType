# ADR 002: Единый механизм линковки

**Дата решения:** 2026-02-23. **Статус:** принято; единый путь сохранён.
Текущая реализация сверена 2026-11-11. Старое указание «v0.2.1, октябрь 2024»
не имело подтверждения и не используется как дата/версия реализации.

## Контекст и решение

Ранняя модель описывала отдельные пути single-package и multi-package linking.
Это дублировало копирование, валидацию и построение metadata, хотя одиночный
пакет является частным случаем списка пакетов. Исправления и incremental
оптимизацию приходилось бы согласовывать между двумя реализациями, а наличие
конфигурационного файла необоснованно меняло набор доступных возможностей.

Принято использовать один pipeline с разрешённым списком пакетов. Без явного
списка текущий executable BT пакет представляется виртуальной записью
`{name:"."}`. Пользователю не требуется отдельная команда или обязательный
конфигурационный файл для обычной линковки одного пакета.

## Реализация и границы

[resolvePackagesToLink/processPackagesLinking](../../packages/bt-cli/src/core/linking/index.ts)
в текущем коде принимают непустой `btconfig.json#linking.packages`, root-only
`linking` либо metadata текущего `package.json`. Затем применяются общие стадии:
обнаружение system dependencies, обработка пользовательских entries, общий
`api_ext.xml`. Типовые linkers сохраняют различие standalone/component/system;
единый pipeline не означает одинаковую инициализацию всех типов.

Старые схемы с top-level `packages`, `platformDir`, `outputRoot`, `buildDir`
и выдуманными CLI flags удалены из этой записи: они были эскизом, а не текущим
контрактом. Действующий JSON, defaults и команды — в
[btconfig reference](../../docs/reference/btconfig.md) и [гайде](../../docs/guides/linking.md).
Без config нужен executable BT пакет; линковка не становится доступной для
произвольной папки или library автоматически. Обычная папка может быть явно
включена с `source`/`target`.

Решение устраняет дублирующий control path, но не доказывает совместимость
output, корректность cache invalidation или incremental metadata. Конкретные
ограничения нормализации executable keys, orphan files и dependency cache
сверены в [текущей теме](../cli/linking-and-cache.md). Для script/module действует
[отдельный memory freeze](2026-11-05-script-module-memory-freeze.md).

## Альтернативы и последствия

- **Два пути с общим helper:** уменьшает дублирование низкого уровня, но сохраняет
  две модели поведения/настройки и необходимость согласовывать будущие изменения.
- **Обязательный btconfig для всех:** упрощает вход pipeline, но добавляет
  шаблонный файл проекту, где достаточно metadata package.json.
- **Отказ от link без config:** лишает простой проект готового dist без
  технической необходимости.
- **Отдельные команды либо пакеты single/multi:** переносит внутреннее разделение
  на пользователя, усложняет переход от одного пакета к нескольким.

Выбрана нормализация входа перед общей реализацией. Небольшая стоимость создания
виртуальной записи принята ради одной модели линковки; отдельного измерения
overhead нет. Общий путь уменьшает дублирование исправлений, но single/multi
cases всё равно требуют проверки их различных inputs и итоговой metadata.
Нельзя выводить полную backward compatibility старых schemas из самого факта
унификации.
