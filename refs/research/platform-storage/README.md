# Карта хранения WebSoft HCM — 2026-11-11

Первый срез структуры SQL-БД и файлов сервера: где находятся полные объекты,
каталоги, blobs, формы, исполняемый код и индексы. Основание для дальнейших
исследований и дополнения skills. Это карта конкретной установки, а не обещание
одинаковой схемы всех версий HCM.

- [Структура БД](database-layout.md): реальные таблицы, поля, связи, индексы,
  предметные области и расхождения с документацией.

  [ФС и разрешённая выборка настроек](observed/filesystem.json),

## Среда и сила доказательств

Исследовался Linux-контейнер `websoft/hcm:2025.2.1333`, image ID
`sha256:0edeac24afc2a5371ea8431c59b1c17ca2b1a9e5a3768275cfdb5023609e34ab`.
PostgreSQL — `16.15 (Debian 16.15-1.pgdg13+2)`, БД `WTDB`, SQL schema `dbo`.
Точный image ID PostgreSQL и SHA256 источников сохранены в manifest.

HCM оставался остановлен. Снимок файлов получен из `docker export` **контейнера
с его writable layer**, затем дополнен инвентаризацией volumes через временный
контейнер с readonly mounts и без сети. Это не чистый дистрибутив: `docker diff`
показывал 1541 изменённый путь, преимущественно FT и временные файлы. Архив
поставки `hcm_2025.2.1333.tar.gz` здесь является Docker image archive, а не обычным
tar с корнем `/WebsoftServer`.

PostgreSQL временно запускался для `REPEATABLE READ READ ONLY` запросов с
`statement_timeout=20s`, `lock_timeout=2s`. Разные SQL-файлы — отдельные snapshots,
не единая транзакция с файловой инвентаризацией. Запросы из `probes/` исполнены
успешно; повтор регистрации дал прежние 1148 записей. Исследование не запускало
`Save()`, HCM agents, SQL-запись бизнес-данных или индексацию. Содержимое полных
XML-объектов, blobs и журналов не читалось; бизнес-данные в git не переносились.
Выборочные vendor source/config читались приватно; опубликованы описание,
locators, hashes и разрешённые поля настроек, без полных файлов и секретов.

В конце временный контейнер удалён, PostgreSQL остановлен; оба исходных
контейнера снова `exited`. Это восстановление состояния запуска, а не утверждение
о byte-for-byte неизменности служебных файлов PostgreSQL после start/stop.

**Текущие доказательства:** PostgreSQL metadata/агрегаты и static source.
**Отдельные исторические доказательства:** C-runtime URL routing и lifecycle
объектов из связанных исследований. Текущая CLR-версия, загруженные DLL,
Windows/MSSQL, cluster и runtime приоритет настроек этим срезом не проверены.
Дата и версия в документации или имени image не заменяют идентичность файлов.

## Что переносить в skills

Пока собрана база, сами skills этим изменением не переписываются. Подтверждённые
правила для будущего дополнения:

1. Сначала различить полный документ, каталог, logical URL, physical file и FT
   индекс. У одного объекта эти представления могут находиться в разных местах.
2. Форму и каталог определять по регистрации/проверенной форме. Удаление `s`
   из имени таблицы, название XML-тега и любой встреченный `id` не дают
   универсального способа открыть объект.
3. Для изменения объекта читать полную форму и полный XML; не собирать replacement
   из каталога и не писать напрямую в его SQL-таблицу.
4. Связь `FOREIGN-ARRAY` проверять по XMD и фактическим ограничениям. SQL-колонка
   `*_id` сама по себе не доказывает ни FK, ни существование объекта назначения.
5. Поиск по ФС не покрывает код в объектах БД, blobs и динамически выбранных
   библиотеках. Расширение файла и наличие DLL не доказывают активное исполнение.
6. Не считать отсутствие карточки в полнотекстовом поиске отсутствием объекта.
   Проверять известный ID или обычный каталог; очереди/расписание FT исследовать
   отдельно от SQL B-tree/GIN.
7. Перед работой с путём учитывать URL scheme, registry roots, storage hook и
   provider settings. Пустой physical `wt_data` не означает пустую систему.

## Следующие измеримые исследования

| Приоритет | Вопрос                            | Достаточный результат следующего шага                                                                                                                                                       |
| --------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1         | Цепочка полнотекстовой индексации | Установить реально загружаемый provider, приоритет двух конфигов и путь индекса; на отдельном owned объекте измерить Save → каталог → FT, документировать запуск/cleanup                    |
| 2         | Построение связок и проекций      | Проследить `group → group_collaborators` и `event → event_collaborators/event_results`: источник строки, ID, rebuild/delete; не распространять результат на все 50 дополнительных каталогов |
| 3         | Resource, URL и binary            | Проследить `resource` XML → `file_path` → disk/blob, проверить обновление/удаление owned вложения и отсутствие остатков                                                                     |
| 4         | Регистрация форм и компонент      | Сопоставить disk XMD, blob XMD, metadata и FetchForm; проверить приоритет, cache/reload и действительное значение ini roots                                                                 |
| 5         | Переносимость                     | Выбрать второй runtime/backend и повторить узкие контракты; различия PostgreSQL/MSSQL не выводить из одного Linux-стенда                                                                    |

Эти шаги пока не выполнены. Перед runtime-частью выбирать ограниченную пробу с
явным cleanup, а не запускать штатный пересчёт/индексацию всей установки.
