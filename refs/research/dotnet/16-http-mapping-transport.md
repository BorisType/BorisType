# Kestrel как транспорт ws-client на работающем HCM

24 ноября 2026, Linux x64, WebSoft HCM 2025.2.1333, одна web-нода, локальный Docker, PostgreSQL, .NET 9. Проверен собственный `IDatexHttpMapping`, запущенный внутри штатного Datex.XHTTP. У входа HTTP проверялись маршрутизация, смена DLL и identity. Прикладные запросы к файлам и документам через новый транспорт ещё не реализованы. Действующий SDK и MCP используют SOAP. [Исходник mapping](../../../packages/dotnet/probes/HttpMapping/Mapping/Mapping.cs) и [исполняемые проверки](../../../packages/dotnet/probes/HttpMapping/verify.py).

## Какие изменения требуют рестарта

Контрольный опыт начинался с обычного HCM. После копирования нашей DLL и изменения `AspNetMappings` новый URL продолжал возвращать 404. После рестарта процесса HCM с этими же файлами заработал собственный обработчик. Это согласуется с CIL поставленной `Datex.XHTTP.dll`: `Startup.Configure` вызывает `IDatexHttpMapping.Initialize` при настройке endpoints, а `Middleware.RegisterAspNetMapping` возвращает false после инициализации Startup. Холодная установка самого mapping в пробе выполнена средствами Docker. Первичная установка через evaluator возможна только с соответствующими правами на установку и отдельным рестартом. [Конфигурация WebSoft](https://wshcm-docs.boristype.dev/news/platform/7277987440881530983.html#ключ-aspnetmappings).

После этого проверены **два способа** добавить HTTP-операцию в живой процесс.

| Действие                                              | Наблюдение                                                                                                                                                                                                                                |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Подготовить `v2` за уже зарегистрированным префиксом  | После установки C по SOAP новый `v2/added` вернул 200. У `v1/added` остался 404.                                                                                                                                                          |
| Добавить самостоятельный URL вне префикса             | Сначала запросили новый URL и получили 404. Mapping опубликовал новый `RouteEndpoint` в своём `EndpointDataSource` и уведомил маршрутизатор через change token. Тот же URL вернул 200 от того же экземпляра mapping.                      |
| Запросить отсутствующую или повреждённую версию       | В свободном слоте отсутствие файлов дало 503, ошибка хеша дала 409. После доставки корректной DLL восемь параллельных запросов получили C, счётчик загрузок составил один.                                                                |
| Подложить повреждённое обновление B для работающего A | Клиент получил фактическую версию A и признак отклонённого обновления. После отдельного рестарта при всё ещё повреждённой B новый экземпляр mapping восстановил A из записи о последней рабочей версии. В слоте v2 продолжила работать C. |
| Обновить A до B при открытом запросе                  | Обработчик отправил начало ответа из A и ждал успешной активации B. Новый запрос получил B, открытый поток завершился ответом из A. В том же процессе v2 ответила C.                                                                      |

Для proof of concept достаточно обычного префикса с диспетчеризацией по major и имени операции. Если операции нужна собственная route metadata, можно зарегистрировать один источник endpoints при старте и обновлять его снимок после проверки сборки. В пробе поздний URL обслуживает фиксированный делегат самого mapping. Диагностические ответы с константами доступны только с loopback. Для прикладных методов проверка пользователя и полномочий нужна на каждом маршруте, включая добавленные позже. Идентификатор mapping, адрес позднего endpoint, HTTP-коды и тела ответов проверяет runner. [Контракт GetChangeToken](https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.routing.endpointdatasource.getchangetoken?view=aspnetcore-9.0).

## Установка первого mapping без изменения xhttp_config.json

25 ноября 2026 на отдельном экземпляре образа `websoft/hcm:2025.2.1333` подтверждён ещё один вход в тот же startup pipeline. HCM сам обнаруживает установленный компонент в `/WebsoftServer/components`, читает его `package.json` с `enableByDefault` и вызывает `init()` до построения маршрутов Kestrel. Наш компонент загружает DLL из собственного каталога `bin`. Та вызывает публичный `Middleware.RegisterAspNetMapping` с полными именами своей сборки и класса. Дополнительная запись в `AspNetMappings` и реестр `source/api_ext.xml` для этого пути не понадобились. Штатный компонент `push_notifications` в поставке использует тот же API. [Формат компонентов WebSoft](https://wshcm-docs.boristype.dev/news/platform/7262821728856765888.html) · [Проверенный компонент, сборка и установка](../../../packages/dotnet/probes/HttpMapping/Component/README.md).

- **На работающем стенде.** Через существующие `WshcmClient`, evaluator и `WshcmUploader` передали один каталог `bt_http_mapping_probe` в `x-local://components/`. SHA-256 всех четырёх файлов совпали с локальной сборкой. До загрузки и сразу после неё URL возвращал 404.
- **При следующем старте.** HCM записал успешную инициализацию компонента, `RegisterAspNetMapping` вернул true. GET с loopback получил 200 и точный маркер из C#-обработчика. Ещё один рестарт без переустановки дал тот же ответ. На обоих стартах SHA-256 исходного `xhttp_config.json` оставался `a3db9ba743525af43d3783d950234ef76e17f6a8f1c016eaf9f438362a1f2f54`. Файл `source/api_ext.xml` отсутствовал.
- **Выбор имени.** Полный успешный прогон выполнен в стандартном пространстве HCM с уникальным кодом `bt_http_mapping_probe`. Вариант с собственным `namespace: boristype` при каталоге без суффикса вызвал ошибку PackageManager ещё до `init`. В каталоге `bt_http_mapping_probe@boristype` загрузчик обнаружил компонент, но для проверенной пары XML/JS не разрешил `init`. Прямой вызов из `OnInit` формы при таком варианте зарегистрировал маршрут, при этом сам компонент остался со статусом ошибки. Поэтому в распространяемом примере используется конфигурация, для которой подтверждены и успешный статус компонента, и HTTP-ответ. В собственный манифест включено `onFailure: "warn"` для ошибок инициализатора. Ошибочное имя каталога может сорвать сканирование раньше.
- **Docker.** Действующий entrypoint нашего стенда при запуске копирует `xHttp.ini` и XML подключения к БД. `xhttp_config.json` в этом сценарии остаётся из образа. Каталог `/WebsoftServer/components` в текущем Compose находится в записываемом слое контейнера. При пересоздании контейнера из исходного образа пакет исчез. Для включения с первого запуска каждой новой реплики достаточно включить каталог в образ; у установки с постоянным каталогом компонентов можно доставлять его туда.

Перед выбором транспорта SDK должен проверить защищённый маршрут и поддерживаемый протокол. При первой установке с правами на запись доставить компонент и сообщить, что Kestrel-транспорт ожидает запуска web-процесса. До этого существующие SOAP-операции доступны. Если файлы уже подготовлены, повторное подключение не должно заново их устанавливать. Для релизной поставки нужен атомарный переход от проверенного staging-каталога к конечному имени, чтобы сканирование при старте не застало неполный пакет. В исследовании устанавливался один фиксированный диагностический компонент, автоматический установщик в SDK отсутствует.

## Смена версии обёртки при рестарте

На отдельной Linux web-ноде HCM 2025.2.1333 два релиза обёртки доставлялись через `WshcmRuntime.stageForStartup()`. Первая реализация пробы сохраняла одинаковое имя сборки. После подготовки V2 и рестарта `active.json` уже содержал V2. В журнале `dotnetcore` WebSoft указал путь к DLL **V1**, HTTP вернул MVID V1. Передача абсолютного пути к V2 в `GetAssembly` не обеспечила выбор файла.

В повторном прогоне логический ID в манифесте остался общим. Сборки получили имена `BorisType.ComponentMappingProbe.V1.0.0` и `BorisType.ComponentMappingProbe.V2.0.0` в метаданных PE. Стабильный `init()` читает `active.json`, запрашивает версионное имя, а метод регистрации сверяет собственный MVID с подготовленным. Диагностический GET на loopback возвращает фактические версию, MVID и идентификатор экземпляра.

| Момент                                                   | Результат                                                                                                            |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Первичная установка через evaluator на работающем стенде | Маршрут вернул 404. После первого рестарта ответила V1.                                                              |
| Подготовка V2                                            | SDK сообщил `installed=V2`, `loaded=V1`. Ответы HTTP до и после подготовки содержали одинаковые MVID V1 и экземпляр. |
| Повторный запрос старого клиента                         | `changed=false`, в указателе осталась V2.                                                                            |
| Следующий рестарт                                        | HTTP вернул MVID V2 и новый экземпляр. Хеши DLL обеих версий сохранились. Хеш `xhttp_config.json` совпал с исходным. |

На Windows в .NET CI загружена DLL V1 и дополнительно открыт handle без разрешения на запись и удаление. Попытка открыть её для записи получила отказ, подготовка V2 прошла. При блокировке самого `active.json` установщик вернул `blocked`, исходные байты указателя сохранились. После снятия блокировки повторная подготовка выбрала V2. Запуск компонента внутри Windows HCM требует отдельного стенда. [Runner и воспроизведение](../../../packages/dotnet/probes/HttpMapping/Component/README.md) · [Windows и Linux CI](https://github.com/BorisType/BorisType/actions/runs/45633951836).

## Первый HTTP-вызов своей DLL без рестарта

Для уже работающей установки есть второй путь. В поставке WebSoft штатная страница `wt/web/wftwt/serve.html` вызывает `user_init.html`, а затем метод managed-сборки. По этому образцу на том же стенде проверена отдельная страница с одним фиксированным методом, возвращающим строковый маркер. [Разбор штатной страницы](../ws-client-runtime/websoft-code.md#подтверждённая-связь-с-установленными-скриптами).

Стенд запустили с исходным конфигом, без BorisType mapping и без новой DLL. При работающем HCM запросили новый URL с Basic и получили 404. Затем через Docker скопировали собственную DLL с уникальным assembly name в `dotnetcore/libs` и страницу в `wt/web`. Страница выполнила штатный `user_init.html`, загрузила DLL через `tools.dotnet_host.Object.GetAssembly` и вызвала фиксированный метод. Следующий HTTP-запрос получил 200 и точный маркер из DLL, анонимный запрос — 401. Идентификатор времени запуска контейнера не изменился, конфиг `AspNetMappings` остался исходным.

Такой вход позволяет обслужить первый клиент сразу, а прямой маршрут Kestrel включить при очередном плановом старте. Каждый запрос через страницу проходит через BorisScript и managed bridge. Отдельно нужно проверять обработку тела запроса и ответа, ограничения размера и права на прикладные операции. Удаление файлов во время работы тоже имеет задержку: непосредственно после удаления тот же URL ещё вернул маркер, при следующей проверке ответил 500. После контрольного рестарта вернулся исходный 404, а штатный вход ответил 200. Оба сервиса стенда снова остановлены. На мгновенный отзыв маршрута удалением страницы рассчитывать нельзя.

Для прямой регистрации в уже запущенном Datex.XHTTP 2.25.12.4 штатного вызова не найдено. В поставленной ASP.NET Core `EndpointRoutingMiddleware` создаёт собственный `CompositeEndpointDataSource` из источников, перечисленных при построении pipeline. Этот конструктор копирует список. Доступ к `Middleware.Host.Services` сам по себе не предоставляет активному matcher новый источник. Подтверждённый выше способ динамически добавить endpoint использует change token источника, включённого при старте.

## Откуда берётся пользователь

В этой конфигурации для хоста используется схема `None`. Во всех строках применялись один и тот же стенд и одна и та же учётная запись. Контрольный маршрут внутри mapping смотрит только `HttpContext.User`. В отчёт попадают счётчики и признаки совпадения, значения cookie и claims в него не включаются.

| Что отправили на HTTP-маршрут                                                    | Результат                                                                                                                                                  |
| -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Анонимно, только Basic, только cookie от штатного входа SDK, Basic с этой cookie | Во всех четырёх случаях 401, ноль authenticated identities и claims. Сам вход SDK на `/spxml_web/main.htm` вернул 200 и `SessionID`.                       |
| Basic и настоящая cookie jar SDK после успешной SOAP-операции                    | Снова 401 и ноль claims. Штатный `/$hcm/checkmessages` с Basic и cookie от входа SDK отдельно вернул 403.                                                  |
| Только `x-auth-id`, выданная при обычном Basic-входе через `GET /home`           | 200, одна authenticated identity, девять claims, имя совпало с логином, присутствовал subject. Штатный `/$hcm/checkmessages` с этой же cookie ответил 200. |
| Следующий независимый запрос без cookie                                          | Снова 401.                                                                                                                                                 |

**Рабочий клиентский сценарий для этого стенда** — войти на портал, принять выданную HCM `x-auth-id`, затем подтвердить пользователя на защищённом маршруте mapping. Для этого запроса хватило одной cookie, без Basic и `SessionID`. Собственный код обработчика не обращался к native Session. Это позволяет обойтись без своего сервиса выдачи токенов. Внутренняя работа middleware WebSoft не измерялась. У штатного `Websoft.Mapping.HCM.CheckMessages` тоже есть проверка `context.User.Identity.IsAuthenticated` и разрешение сотрудника по claims/логину. [Раздел Authentication в документации WebSoft](https://wshcm-docs.boristype.dev/news/platform/7277987440881530983.html#секция-authentication).

Подтверждённый логин ещё не устанавливает права сотрудника на объект. Для включения прикладной операции нужно проверить права по правилам этой операции и повторить один разрешённый и один запрещённый вызов под разными пользователями. Для удалённого стенда SDK должен передавать учётные данные по HTTPS и привязывать cookie к origin и пользователю. Наличие страницы `/home`, выдачу ticket, срок действия и поведение на следующей ноде определяет установка.

## Какой контракт брать в реализацию

- **На стенде** один маленький mapping. Его можно поставить как саморегистрирующийся компонент в отдельном каталоге. Его стабильные обязанности — принять запрос, установить пользователя, выбрать совместимый backend и вернуть фактическую версию и возможности. Конкретные HTTP-операции можно добавлять внутри этого контракта. Изменение ABI самого mapping планировать как обновление с рестартом.
- **Версия относится к протоколу и сборке, пользователь — к запросу.** Клиент выбирает поддерживаемый major. Несколько клиентов могут обращаться к одной и той же DLL с разными правами. Подключение старого клиента не должно записывать глобальный указатель на старую сборку. Установку разрешённых сборок и выбор версии для новых запросов контролирует операторская политика.
- **Обновление** сначала помещает полный артефакт в отдельный каталог, проверяет доверенное происхождение, совместимость, зависимости и возможность загрузки. Затем атомарно публикует выбранную версию. Сохранять и фактически принятую версию для следующего старта. При нескольких установщиках запись желаемой версии требует блокировки или compare-and-swap с номером поколения. Эта проба проверяет конкуренцию читателей одного процесса и обычный рестарт. Устойчивость к потере питания не измерялась. Если обновление не удалось, discovery сообщает реально обслуживаемые операции и причину отказа. В пробе доверенными заранее были три SHA-256, а у трёх сборок разные assembly simple names. В production нужен способ допускать следующие релизы без изменения startup-конфига. Один из вариантов — подписанный манифест с заранее установленным ключом.
- **Разные имена файлов сами по себе не решают конфликты CLR.** Проба загрузила сборки без частных зависимостей. Для зависимостей с одинаковым simple name нужен отдельно проверенный `AssemblyLoadContext` с общим контрактом на стороне host либо совместимые версии зависимостей. Проба держит загруженные сборки до завершения процесса. Нужен предел числа сохраняемых сборок и явное обслуживание при его достижении. [О границах AssemblyLoadContext](https://learn.microsoft.com/en-us/dotnet/core/dependency-loading/understanding-assemblyloadcontext).
- **Выбор транспорта** происходит до прикладной операции. SOAP evaluator остаётся доступным для установки на разрешённом стенде. Если mapping ещё не обслуживает нужный протокол, клиент может заранее выбрать поддерживаемую SOAP-операцию. 401/403 прикладного вызова должны вернуться вызывающему. Потеря ответа после записи оставляет результат неизвестным. Автоматический повтор такой записи через SOAP может применить её дважды.
- **Кластер** требует готовности каждого обслуживающего процесса, проверки ticket между нодами и схемы развёртывания. Один удачный handshake через балансировщик не даёт гарантии для следующей ноды. Перед включением по умолчанию также проверить ограниченную учётную запись, истечение/обновление ticket, Windows HCM и хотя бы одну настоящую операцию с правами, отменой и ошибками. Ранее найденные ограничения BS↔.NET и native-контекста продолжают действовать. [Предыдущее исследование bridge](../../dotnet/bridge.md).

## Как воспроизвести

Нужны отдельный запущенный Linux Docker HCM со штатным маршрутом `$hcm/checkmessages`, локально опубликованным портом 80 контейнера, `bash` и `timeout` внутри контейнера. Снаружи нужны Docker CLI, Python 3, Node/pnpm и .NET SDK проекта. Используются `Websoft.Commons.dll` и `Datex.log.dll` из целевой поставки. **Runner трижды перезапускает приложение**, меняет `/WebsoftServer/xhttp_config.json` на время опыта и требует, чтобы тестовый mapping изначально отсутствовал. Временные payload и указатели доставляются штатным evaluator из текущего checkout. [Runner](../../../packages/dotnet/probes/HttpMapping/run.py) и [установка fixture](../../../packages/dotnet/probes/HttpMapping/install-fixture.mjs).

Из корня checkout, с уже заданными `WSHCM_USERNAME` и `WSHCM_PASSWORD` тестовой учётной записи, имеющей доступ к evaluator:

```sh
pnpm install --frozen-lockfile
pnpm --filter @boristype/ws-client build
python3 packages/dotnet/probes/HttpMapping/run.py "$HCM_CONTAINER" "$WEBSOFT_REFERENCE_DIR"
```
