# URL API и физическая ФС: SQL blobs

Дата: 2026-11-06. Native research по замечанию пользователя о `DESIGN-DB`,
`DATA-DB` и `spxml_blobs`. Изменений production code нет.

## Результат

Подтверждено: `LoadUrlData(x-local)` может читать SQL blob вместо диска, хотя
`UrlToFilePath` возвращает существующий физический путь. На `wt_data` с SQL hook
`PutUrlData` менял blob, сохраняя прежние байты дискового файла. `x-app` и `file`
в этом эксперименте читали диск. После удаления физического файла `x-local`
продолжал читать blob.

Дополнительно установлено: при отсутствии blob `LoadUrlData(x-local)` импортировал
файл с диска в SQL. `LoadFileData`, `LoadUrlData(x-app)` и `LoadUrlData(file)` на
новом контрольном имени этого не делали. `DeleteUrl(x-local)` удалил blob,
сохранив физический файл. Последующее чтение могло снова импортировать диск.

Переносимые сведения, источники и порядок воспроизведения:
[URL storage reference](../../../skills/websoft-hcm/references/url-storage-and-blobs.md).

## Конфигурация и контроль

Linux x64 HCM 2025.2.1333, CLR 9.0.11, assembly 2.25.12.4 [202512041524],
PostgreSQL, прежний локальный stand `boristype-c-runtime-net9`.
Image ID: `sha256:0edeac24afc2a5371ea8431c59b1c17ca2b1a9e5a3768275cfdb5023609e34ab`.
Carrier — authenticated ws-client eval во временной BS-библиотеке,
smoke `2 + 2 → 4`, без адаптации BS source.

Проверены три существующих корня:

| Корень    | Настройки                                                            | PutUrlData     | Независимый контроль                                   |
| --------- | -------------------------------------------------------------------- | -------------- | ------------------------------------------------------ |
| `wt`      | DESIGN-DB, без активного SQL hook                                    | Изменяет диск. | SQL row отсутствует; cat читает новый маркер.          |
| `share`   | DATA-DB, без SQL hook                                                | Изменяет диск. | SQL row отсутствует; cat читает новый маркер.          |
| `wt_data` | DATA-DB + DB-STORE-HOOK на `platform/storage/spxml/sx_store_sql.xml` | Изменяет blob. | SQL SELECT читает новый маркер; cat сохраняет прежний. |

SQL проверялся прямым `psql` по точным URL наших fixtures в
`dbo."(spxml_blobs)"`: `url`, `octet_length(data)`, `encode(data,'escape')`.
Схема проверена через information_schema; `data` — `bytea`.
Чужие blobs и содержимое пользовательских файлов не читались.

Матрица read-routes: три корня × три схемы; отдельные этапы до PutUrlData,
после записи, после прямого изменения диска, после удаления диска, после
DeleteUrl и после возвращения файла при отсутствующем blob. Каждый carrier
завершён до изменения fixtures и следующего запуска.

Свежая hydration fixture проверена четырьмя последовательными чтениями с
SQL SELECT между ними: physical → x-app → file → x-local. Только последний
создал SQL row с тем же ASCII-маркером. Никакого предварительного PutUrlData
для этого имени не выполнялось.

## Что выяснилось о регистрации корней

Сделана отдельная конфигурационная проба с новыми физическими каталогами
`bt_probe_design_0yggwahs` и `bt_probe_data_0yggwahs`. До регистрации оба
отклонялись. Добавлены соответственно DESIGN-DB и DATA-DB, без нового store hook.

Первый запуск не применил правку: stand entrypoint перед запуском копирует
`/tmp/wt/xhttp.ini` в `/WebsoftServer/xHttp.ini`. Он исключён из доказательства
влияния настроек. Затем изменён источник шаблона с проверкой активных байтов
после restart. Однако оба новых host всё равно отклонялись. Повтор с LF,
как в исходном Linux ini, дал тот же результат; гипотеза о CRLF не подтвердилась.

Поэтому причинная связь «добавить одну из этих строк → разрешить новый host»
**не установлена** на этом carrier. Это отрицательный результат для конкретных
новых корней и конфигурации. Причина и полный механизм регистрации остаются
открытыми; документированные назначения параметров не переопределяются
этой пробой. Изменять параметры по аналогии без проверки нельзя.

Отдельное включение/отключение SQL hook не тестировалось. Наблюдение `share`
достаточно опровергает универсальное утверждение «DATA-DB всегда отправляет
в SQL», но не устанавливает всех условий выбора storage provider.

## Следствие для текущих tools

Managed FileSystem принимает физические пути и работает через System.IO.
Bridge `UrlToFilePath` не переносит SQL storage semantics. Поэтому tools могут
читать/изменять дисковую копию, отличающуюся от ресурса того же x-local URL,
который видит `LoadUrlData`. Read grants и hashes относятся к физическим байтам.
Для логических URL/blob операций нужен отдельный контракт и backend;
расширение списка схем само по себе проблему не решает.

Это ограничение добавлено в MCP guide и package README; код tools в этом шаге
не менялся. Кластерная работа, Windows HCM и VFS/S3 native не проверялись.
