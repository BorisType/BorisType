# Следующие этапы файловых MCP tools

Дата: 2026-11-06. Запись согласованного состава tools, требований к учёту чтения
и границ гарантий до реализации (alpha.3). Итоговый контракт alpha.4 —
[учёт чтений](11-read-aware-files-design.md), [результаты](13-read-aware-files-results.md).
Текущая реализация и evidence: [контракт](07-file-tools-design.md),
[результаты](09-file-tools-results.md).

## Состав инструментов

Целевое ядро — девять tools: существующие read_file, write_file, list_directory,
delete_file, search_files, edit_file и будущие create_directory, move_file,
get_file_info. В MCP у всех имён префикс `wshcm_`.

Move должен использовать файловое перемещение без перезаписи назначения;
read/write/delete не являются допустимой скрытой заменой этой операции.
Ограничения перемещения между файловыми системами требуют явного контракта.
Get-info получает metadata без чтения всего содержимого, включая binary files
и каталоги. Create-directory закрывает требование существующего parent у write.

Read-multiple-files отложен до оценки стоимости нескольких SOAP requests.
Directory-tree пока не планируется отдельным tool: сначала рассмотреть bounded
recursive listing. Search не заменяет дерево полностью, поскольку не показывает
пустые каталоги. Чтение диапазонов текста нужно для следующего этапа.
Неиспользуемые TS/BS заготовки не определяют публичный API; их удаление отдельно
от реализации новых tools. Действующие BS bridges для URL resolver остаются.

## Цель учёта чтения

Задача — запретить изменение содержимого, которого агент не получил в текущей
области учёта чтений. Предотвращение потери параллельных изменений — только часть
этого требования. Одного предоставленного клиентом hash или oldText недостаточно
для подтверждения предшествующего чтения.

Следующий этап должен учитывать файл, hash исходных bytes и фактически выданные
диапазоны текста. Запрошенный, но не возвращённый диапазон не считается прочитанным.
Редактируемые участки должны быть полностью покрыты чтениями той же версии.
При несовпадении текущих bytes с прочитанной версией требуется новое чтение;
автоматического совмещения с внешними правками на первом этапе нет.

Полная перезапись существующего файла требует чтения всего содержимого.
Политика должна охватывать edit и overwrite через write; создание нового файла
должно явно запрещать перезапись существующего назначения. Удаление и перемещение
требуют отдельных условий и не означают чтение всего binary file.

Разделение ответственности: MCP хранит состояние чтений и проверяет диапазоны;
DLL проверяет текущую версию непосредственно перед изменением. Hash/precondition
не заменяет учёт чтения в MCP. Сейчас этого учёта нет: expectedSha256 у edit
необязателен, а write допускает безусловную перезапись.

До реализации определить формат read-token, bounded lifetime/объём состояния,
идентичность файла после URL resolution, координаты диапазонов и их изменение
после собственных последовательных edits. Проверять отсутствие чтения, чтение
в другой области учёта, устаревшую версию, неполное покрытие и обход через write.

## Граница сессий

Учёт должен принадлежать отдельному экземпляру MCP server/соединению и не быть
глобальным для процесса или пользователей. При новом экземпляре прежние чтения
не засчитываются. Это не доказывает изоляцию между чатами агента: клиент может
переиспользовать тот же экземпляр MCP между разговорами.

**Разделение по сессиям/чатам агента не гарантируется**, если клиент не предоставляет
надёжную границу их жизненного цикла. Для такой гарантии потребуется отдельный
экземпляр MCP на сессию агента либо интеграция с клиентом. Сервер фиксирует выдачу
текста клиенту, а не получение или осмысление текста моделью после обработки ответа.

## Гонка после проверки: отложенное исследование

Сейчас edit повторно сравнивает исходные bytes перед rename. MutationLock
сериализует собственные mutations в одном загруженном экземпляре библиотеки;
произвольные внешние процессы ему не подчиняются. Между последним сравнением
и заменой файла внешний writer может изменить назначение, и его изменение
может быть перезаписано. **Атомарный compare-and-replace относительно внешних
writers не гарантируется.** Учёт прочитанных диапазонов эту гонку не устраняет.

Рекомендация: сохранить текущую повторную проверку и явное ограничение;
реализацию строгого межпроцессного протокола отложить. Обычный lock-файл сам
по себе не обеспечивает договорённость с платформой и другими редакторами.
Блокировки и взаимодействие с rename требуют отдельной проверки на Linux/Windows.

Отдельная задача исследования:

- Определить участвующих writers и файловые системы; различать cooperative
  locking и гарантии относительно произвольной внешней записи.
- Исследовать доступный механизм атомарной проверки и commit либо обязательного
  участия всех writers; явно описать ограничения выбранного решения.
- Проверить окно между последним сравнением и rename отдельным процессом,
  с детерминированной синхронизацией, без надежды на случайные задержки.
- Подтвердить контракт на Linux и Windows; managed tests не считать HCM evidence.

Исследование строгой атомарности не блокирует учёт чтений и диапазонов. До его
завершения не описывать optimistic hash check как строгий cross-process CAS.
