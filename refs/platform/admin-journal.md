# Журнал взаимодействия с админкой и порталом HCM

Для каждой записи указывай интерфейс, маршрут, результат и источник. Если на
поведение влияют версия HCM, роль или состояние записи, добавляй эти условия.
Отмечай отдельно наблюдения в браузере, маршруты со слов пользователя,
документацию, чтение XMD/XMS и пробы через MCP. Если изменялись данные,
зафиксируй, как был проверен результат и что удалили после проверки.
Пароли, cookies и данные сотрудников не сохраняются.

Когда сценарий воспроизводится и пригодится на других установках, переноси
ключевые шаги, предпосылки и способ проверки в reference соответствующего
скилла. В журнале отмечай, где опубликован рецепт.
[Правила ведения скиллов](../../skills/README.md)

## 2026-11-17: пакеты объектов

Стенд: Linux C-runtime WebSoft HCM **2025.2.1333**, PostgreSQL 16, CLR 9;
веб-администратор `/spxml_web/main.htm`, Chrome 157. Исследование выполнено через
Chrome DevTools MCP 1.13. Образ стенда:
`sha256:0edeac24afc2a5371ea8431c59b1c17ca2b1a9e5a3768275cfdb5023609e34ab`.

Пользователь объяснил следующие маршруты:

- Нижняя левая шестерёнка → **«Содержимое пакета…»**: просмотр текущего пакета,
  создание/сохранение именованной схемы и выбор сохранённой, удаление элементов,
  сохранение ZIP.
- В каталоге администратора, например «Сотрудники»: выделить объекты → ПКМ →
  **«Добавить в пакет»**.
- Верхняя шестерёнка выбора модуля → **«Системное администрирование»** → обработка
  пакетов: загрузка архива и применение к базе.

Пользователь уточнил границы «Добавлять связанные объекты»: штатная логика опирается
на объявленные в XMD связи. Hex-ссылки в `wvars` у `custom_web_template` и
`override_web_template`, а также строковая связь `mode` с `web_mode` могут оставаться
за пределами обхода. Для будущего собственного разрешения этих связей нужен отдельный
флаг, независимый от штатного. Прямой экспорт по IDs нужен для переноса больших
наборов между стендами без сохранения схемы и изменения текущего пакета.

Проверено в браузере:

- Нижняя шестерёнка имеет DOM id `view_panel_settings_btn`; меню содержит
  «Содержимое пакета…», открывается окно **«Объекты пакета»**.
- Окно содержит поле «Схема», выбор/сохранение/создание/удаление схемы,
  **«Сохранить полный пакет…»**, вкладки «Объекты базы», «Файлы»,
  «Настраиваемые поля», «Роли доступа», кнопку **«Создать пакет в базе»**.
- Исходное состояние при входе: схема `novyy`, id `irsd`, 0 объектов. Это существующее
  состояние стенда, не тестовый fixture. Его содержимое не изменялось.
- При открытии UI запрашивает `GetDoc` для
  `x-local://wt_data/lists/wtv_package_objects.xml` и форму
  `x-local://wtv/wtv_package_objects.xms`. Ответ `GetDoc` содержит список схем.
  Это логический URL: наблюдение не доказывает физический файл на диске.
- Верхняя шестерёнка этого стенда имеет DOM id `BlockSwitcher_prop`; открывает
  **«Системное администрирование»**. Пункт **«Обработка пакетов»** загружает каталог
  `download_package`; кнопка **«Обработать пакет»** открывает загрузку файла.
  `BlockSwitcher_admin` относится к модулю «Дизайнер», это другая кнопка.
- Собственный тестовый ZIP загружен; preview показал список вложенных пакетов.
  Нажатие строки пакета раскрыло «Объекты каталогов (1)» с тестовым объектом.
  Есть отдельные «Отмена» и «Применить». Проверка закончилась отменой до применения.
  [Native-проба, очистка и предлагаемый контракт](../mcp/object-packages.md).

Статическая проверка поставки этого же стенда:

- `wtv/wtv_package_objects.xmd` описывает несколько `package_object`, у каждого
  собственные id/name, объекты id/eid/name/type/modify, файлы, настройки custom
  templates/access roles. Имя схемы и идентификатор различаются.
- `wtv/wtv_package_objects.xms` выбирает схему через `local_settings.package_id`;
  сохраняет общий документ схем, экспорт вызывает `ms_tools.create_package_objects`.
  «Создать пакет в базе» вызывает серверный `tools.create_package` и создаёт
  запись `upload_package`; это отдельная операция от сохранения схемы.
- В `wtv_custom_web_template.xmd` и `wtv_override_web_template.xmd` поле `mode`
  объявлено строкой без `FOREIGN-ARRAY`; оба типа наследуют `web_variables_base`.
  `tools.add_object_to_package` ищет ссылки по `ForeignArrayCodeStr`, что подтверждает
  причину пропуска строковых связей. Конкретные ссылочные `wvars` live-пробой не проверялись.

Документация согласуется с основными маршрутами, но не заменяет runtime-проверку:

- [Формирование пакета](https://wshcm-docs.boristype.dev/news/monolith/6738779645850949369.html).
- [Создание пакетов и схем](https://wshcm-docs.boristype.dev/news/monolith/7261342547182835672.html).
- [Обработка загруженного пакета](https://wshcm-docs.boristype.dev/news/monolith/6739766340687312103.html).

Сохранение в базе может участвовать в обмене между серверами. Нельзя использовать
эту кнопку как безусловный синоним «сохранить ZIP».

## 2026-11-20. Настраиваемые поля в пакете

Пользователь уточнил маршрут «Содержимое пакета…» → «Настраиваемые поля».
Флажок обработки и список типов соответствуют `process_custom_templates`
и `custom_templates/catalog_name` в схеме. В `wtv_package_objects.xms`
выбор типа сам включает обработку. В списке выбирается раздел реестра:
`request_type` упаковывает все настроенные шаблоны типов заявок. Выбор
одной строки внутри `request_type.items` в этой форме отсутствует.
Вкладка поддерживает и архив только с определениями.
[Формирование пакета данных](https://wshcm-docs.boristype.dev/news/monolith/6738779645850949369.html)

Источник маршрута — пользователь, документация и статическая сверка XMS.
Сборка с этими параметрами и импорт проверены отдельно через CLI/stdio/SOAP
на том же образе. [Проверка пакета с определениями](../mcp/object-packages.md#пакеты-с-настраиваемыми-полями)

## 2026-11-20. Типы данных объектов

Карточки типов находятся в **Дизайнер → Справочники → Типы данных объектов**.
Для полей конкретной карточки откройте нижнюю шестерёнку, затем
**Настраиваемые поля → Тип данных объектов → Добавить объект**.
Поле «Отображать в блоке» определяет, где появляется список экземпляров.
Маршрут взят из документации и сверён с поставляемыми XMS. Создание типа,
настройка полей и запись экземпляра проверены через MCP.
[Модель и нативная проба](../research/mcp/object-data.md)

## 2026-11-20. Админка и сохранение настраиваемых полей

В веб-админке HCM 2025.2.1333 проверен маршрут через нижнюю шестерёнку
**Настраиваемые поля**. Для типа заявки сначала выбирается существующая
карточка через **Добавить объект → Применить**, затем настраиваются её поля
и страницы. После диалогов нужно сохранить всё окно и открыть его снова
для проверки. В пробе сохранились страница и порядок вариантов поля.
Удаление пробного шаблона через окно оставило карточку типа заявки в каталоге
и восстановило прежний XML реестра.
[Браузерная проверка](../research/mcp/custom-field-templates.md#сохранение-в-админке)

## 2026-11-20. Журналы сервера

В разделе **Системное администрирование → Диагностика → Журналы сервера**
можно выбрать тип журнала и даты, нажать **Показать**, затем выбрать строку
файла. Его текст открывается в нижней части окна. В кластере эта страница
показывает журналы ноды текущего подключения. Журналы запуска агентов ищут
на соответствующей worker-ноде.
[Просмотр журналов](https://wshcm-docs.boristype.dev/news/monolith/6849284012446057252.html)
· [Сбор журналов в кластере](https://wshcm-docs.boristype.dev/news/monolith/7234153256332551015.html)

Маршрут взят из документации. Статическая сверка поставки Linux HCM
2025.2.1333 подтвердила, что `wtv_view_server_log_report.xms` вызывает
`tools_report.server_log_report` для списка и `tools.load_url_data_server`
для чтения выбранного журнала. Первый метод перечисляет `.log` из
`x-local://Logs`, при ошибке пробует каталог `Logs` под `AppDirectoryPath()`.
Второй при размере от 10 MiB читает хвост через `LoadFileDataRange`,
в остальных случаях читает файл целиком. Отдельного запуска страницы в этой
проверке не было.

В этой поставке фильтр «Журнал запросов» (`sql`) относится к группе
в интерфейсе. `tools_report.server_log_report` назначает группу по первой
известной подстроке имени файла и использует `sql`, если ни одна не подошла.
Так в группу попадают `dotnetcore`, `spxml_unibridge` и `auth-events`.

В томе остановленного контейнера найдены дневные файлы с именами
`xhttp_YYYY-MM-DD.log`, `agent_YYYY-MM-DD.log` и более длинными кодами,
включая точки. `dotnetcore_2026-11-20.log` занимал 1 255 402 байта.
В выборке были LF, CRLF и строки без временного префикса. Содержимое
журналов в репозиторий не переносилось.

## 2026-11-20. Проверка выборок, показателей и запуск агентов

В поставке HCM 2025.2.1333 кнопки проверки в карточках выборки и показателя
вызывают серверные методы `ms_tools`. Карточка агента содержит две команды,
`StartAgent` и `StartAgentAdmin`. Первая вызывает `tools.start_agent` на
сервере, вторая запускает метод формы из текущего окружения администратора.
Маршруты установлены по XMS. Фактический runtime второй команды в веб-клиенте
предстоит подтвердить.
[Штатные точки входа и план проверки](../mcp/executable-objects.md)

Пользователь уточнил, что проверка в карточке выборки может падать, если
она рассчитывает на окружение виджета LPE. В коде поставки для портального
вызова найдены подготовка `curContext` по типу страницы и подстановка
параметров виджета перед запуском выборки. Браузерный запрос ItemList на
странице **Сообщество → Новости** повторён из отдельной сессии. На той же
поставке временный виджет подтвердил `curContext`, фильтр, параметр шаблона и
вторую страницу. Штатный ответ ItemList может скрыть ошибку выборки за
выдачей из нуля строк.
[Маршрут LPE](../mcp/executable-objects.md#выборки-в-lpe-и-через-soap)
