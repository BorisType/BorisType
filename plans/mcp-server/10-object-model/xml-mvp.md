# Нативный XML: уточнение MVP и проверка C-runtime

Дата: **2026-11-10**. Это продолжение исследования, а не реализованные MCP tools.
Пользователь уточнил scope: раскрытая XMD, XML объекта, создание и полная замена
объекта из XML. Первоначальная рекомендация типизированного patch из
[tool-options](tool-options.md) заменена этим направлением.

## Представление и транспорт

Данные остаются XML от чтения до записи. JSON нужен для аргументов MCP и
служебного ответа: ID строкой, URL формы, статус, XML-строка. Сериализацию JSON
выполняет клиент протокола; агент не вызывает `EncodeJson` вручную. XML escaping
внутри данных (`&amp;`, `&lt;` и т. п.) остаётся обычным правилом XML.

Возвращать агенту XML можно текстовым content block; structured result при
необходимости содержит ту же строку. JSON transport не требует превращать
элементы XML в JS objects или изобретать представление отсутствующих значений,
массивов и platform-specific scalar types.

Структурный разбор XML для проверки root/ID/полей допустим. Это проверка входа,
а не промежуточная редактируемая модель, из которой заново строится объект.
До платформенного parser доходит исходный XML, прошедший проверки.

## Раскрытая форма уже сериализуется платформой

Рабочие свойства C-runtime:

```javascript
var form = FetchForm(formUrl);
var formXml = form.Xml;
var rootSchemaXml = form.TopElem.Xml;
```

Документация [XmlForm.Xml](https://wshcm-docs.boristype.dev/datex/common/5791375928854454848.html)
обещает канонический XML с дочерними элементами. Декларации revision
`a3b1e43d0b2add53bbc1f2acc2c5128360e8c97b` содержат `Xml: string` в
[xmlform](https://github.com/wshcmx/types/blob/a3b1e43d0b2add53bbc1f2acc2c5128360e8c97b/lib/xmlform/index.d.ts#L51)
и [xmlformelem](https://github.com/wshcmx/types/blob/a3b1e43d0b2add53bbc1f2acc2c5128360e8c97b/lib/xmlformelem/index.d.ts#L179).
Это источники API; раскрытие проверено отдельно на C-runtime.

Собственная [xml-core.bs](probes/xml-core.bs) регистрирует только in-memory форму:
`base SAMPLE="1"`, наследующий root, составное поле `TYPE="base"` и вложенный
массив с наследованием. `TopElem.Xml` содержит раскрытые поля во всех трёх
местах; `TYPE`, defaults, `MULTIPLE` и `PRIMARY-KEY` примитивных полей сохранены.
`Form.Xml` дополнительно содержит `SPXML-FORM` и определение sample.

Это позволяет отдать агенту структуру нужного корня без самостоятельного обхода
файлов. Но нельзя обещать, что экспорт формы полностью самодостаточен для
повторной регистрации: в прежнем native-экспорте vendor catalog сохранился
верхнеуровневый `USE`, хотя унаследованные поля уже были раскрыты. Утверждение
«любые USE исчезают, весь XMD можно перенести одной строкой» не проверено.
Результат нужно обозначать как текущую загруженную форму, не как исходный XMD
или гарантированно актуальные байты файла после изменения кэша.

## Какие входы платформа принимает

Для каждого входа выполнен `OpenDocFromStr(xml, 'form=' + ownFormUrl)`.
Default обязательного integer-поля в собственной форме равен 7.

| Вход                                       | Наблюдение C-runtime                                            |
| ------------------------------------------ | --------------------------------------------------------------- |
| Корректный XML                             | Значения и вложенная структура прочитаны, default добавлен      |
| `<probe/>`                                 | Документ только с default=7                                     |
| Пустая строка, plain text, незакрытый root | Ошибка `End of file`                                            |
| Несовпадающие открывающий/закрывающий теги | Ошибка `Invalid format`                                         |
| Чужой root с непустыми данными             | Успех; ожидаемый root, входные данные потеряны, остался default |
| Неизвестное поле                           | Успех; поле отброшено                                           |
| Два корневых элемента                      | Успех; прочитан только первый                                   |
| Два экземпляра scalar                      | Успех; последнее значение побеждает                             |
| `NaN` в integer                            | Успех; неверное значение заменено default=7                     |
| Необъявленная entity                       | Успех; принята как буквальный текст и затем экранирована        |

Это конкретные наблюдения одного runtime, не общий XML conformance report.
Предыдущая проба присваивания неверной строки непосредственно integer-полю
давала исключение. Импорт из XML ведёт себя иначе; нельзя подменять одну
проверку другой.

Локальный `fast-xml-parser@5.11.2`, `XMLValidator.validate`, отклонил пустой/plain/
незакрытый/несогласованный XML и два root. Однако принял чужой root, неизвестное
поле, дубликат scalar, неверный integer и необъявленную entity. Это отдельное
[Node-наблюдение](observed/xml-local-validator.json), а не проверка C-runtime.
Один `XMLValidator.validate(...) === true` не заменяет проверку схемы и не даёт
основания обещать полную XML-валидацию.

## Создание и полная замена из XML

Собственная [xml-crud.bs](probes/xml-crud.bs) использовала полную форму
`x-local://wtv/wtv_cost_center.xmd` и только ID, выделенный самой платформой:

```javascript
var candidate = OpenDocFromStr(xml, "form=" + fullFormUrl);
candidate.BindToDb(DefaultDb); // создание: новый ID
candidate.Save();

var replacement = OpenDocFromStr(replacementXml, "form=" + fullFormUrl);
replacement.BindToDb(DefaultDb, Int(existingId));
replacement.Save();
```

Подтверждено создание с точным ID, заполнением `doc_info.creation`, чтение по
этому ID и замена: пропущенный во втором XML `comment` стал пустым. Это **replace**,
не merge. Ранее исследованный `LoadData` сливает данные; его нельзя незаметно
использовать как эквивалент полной замены.

Затем та же проба передала `<not_cost_center>...данные...</not_cost_center>`.
Парсинг дал пустой `cost_center` с default `is_active=1`. Привязка к собственному
существующему ID и `Save()` прошли; code/name были очищены. Объект восстановлен
из ранее прочитанного XML, затем окончательно удалён и независимо проверен.
Таким образом, риск потери данных подтверждён вплоть до реального сохранения.

Ограничения этого пути:

- У `OpenDocFromStr` свойство `NeverSaved=false` уже до BindToDb; эквивалентность
  `OpenNewDoc` и его `OnCreate` не доказана. Типы с init hooks требуют отдельной
  проверки. `cost_center` не содержит собственных save hooks.
- В диагностическом запуске установка одного `.Url` без корректной identity
  завершилась provider error из-за пустого ID. Это не защита от плохого XML:
  корректный BindToDb с тем же ID воспроизвёл очистку данных.
- Нельзя подставить частичную/каталожную форму или позволить XML выбрать другую
  форму. Для существующего объекта источник полной формы — сам объект.
- XML не обещает lossless storage backup: TEMP, external data, defaults,
  нормализация чисел, hooks и metadata сохраняют свои платформенные особенности.

## Маленький MVP

Рабочие имена ниже иллюстрируют разделение, окончательная JSON schema ещё не
реализована.

| Операция            | Вход и результат                                                                                                                                                                                         |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `wshcm_get_form`    | Явный URL формы → actual URL, root name и XML раскрытого root. Для чтения формы существующего объекта использовать его actual form                                                                       |
| `wshcm_get_object`  | Точный строковый ID → ID, actual form URL, XML полного объекта; каталог не заменяет этот результат                                                                                                       |
| `wshcm_save_object` | Явный режим create/replace и XML. Create задаёт полную форму; replace задаёт существующий ID и использует его форму. Результат содержит identity и проверенный readback XML либо явный неизвестный исход |

MVP ограничивается операциями над одним документом. Typed JSON/patch DSL,
удаление, bulk, UI-бизнес-команды и migrations не нужны для этой вертикали.
Сохранение выполняется платформенным BS API, .NET object mapper не требуется.

Минимальная защита до `Save`, которую нужно специфицировать и покрыть negatives:

1. Непустой XML, один root, корректное закрытие тегов; ограничение размера/глубины.
   DTD/external entities и управляющие формой инструкции во входных данных
   отклоняются. Пользовательская строка не подставляется как BS-код или options.
2. Проверить **входной** root по полной загруженной форме. Проверять только
   `candidate.TopElem.Name` поздно: платформа уже заменила неправильный root.
3. Проверить точную identity: несовпадающий XML ID отклонить, replace отсутствующего
   объекта не превращать в create, подмену actual form запретить.
4. По метаданным формы отвергать неизвестные data-поля и повторения singleton.
   Это узкая проверка структуры, не универсальная модель или XSD validator.
5. Отдельно определить проверяемые scalar types. Для первой вертикали неверный
   integer из negative-пробы должен быть отклонён до записи. Остальные преобразования
   типов нельзя называть проверенными, пока нет соответствующих native cases.

Readback после Save полезен, но не предотвращает уже совершённую потерю данных.
Проверка parse/normalize до Save не является безопасным dry-run: загрузка формы
и инициализация тоже могут выполнить код. Byte-for-byte сравнение XML непригодно
из-за defaults, форматирования, order и нормализации значений.

Для whole replace принцип чтения перед записью относится ко всему документу:
частичный/обрезанный ответ не должен разрешать замену. Точный контракт session
token и compare-before-save — отдельный пункт следующей spec; атомарный CAS не
обещается. Ошибки hooks, timeout, отсутствие rollback и неповторение UI permissions
сохраняют ограничения из [tool-options](tool-options.md).

## Воспроизводимость и очистка

Среда: Linux x64, `websoft/hcm:2025.2.1333`, assembly
`2.25.12.4 [202512041524]`, .NET 9.0.11, PostgreSQL 16, legacy object model.
Carrier — authenticated SOAP evaluator, не `main.js`. Source/transcript hashes
и cleanup записаны в [xml-evidence-manifest.json](xml-evidence-manifest.json).
Старые 59 assertions проверяются прежней командой независимо.

```sh
node plans/mcp-server/10-object-model/probes/verify-xml-results.mjs
```

Команда проверяет сохранённые наблюдения, hashes и независимый cleanup receipt;
она не обращается к стенду и не тестирует реализацию tools. Пробы содержат
преднамеренно разрушающий negative только на собственном объекте; не запускать
на production. Переносимые транскрипты не содержат vendor schema source.
Результат: **53/53 проверки записанных native-наблюдений и целостности evidence**,
отдельно проверяется локальное Node-сравнение. Два отрицательных контроля verifier
прошли: изменённый source отвергается; подмена результата wrong-root отвергается
даже после пересчёта hash транскрипта в копии manifest.

Оба выделенных за сессию ID (`7349577609794908305`, `7349577710243911718`)
независимо проверены: cost_centers=0, trash_docs=0, `OpenDoc` не открывается.
Docker filesystem не содержит `unsafe_eval_*.bs` и собственных `boristype_xml_mvp_*.xmd`.
Проверка сделана после evaluator cleanup. WT и PostgreSQL возвращены в исходное
остановленное состояние; exit 143/0, оба `OOMKilled=false`. Memory-only формы
освобождены остановкой процесса; API eviction не доказан.
