# Варианты MCP API для объектов и следующие этапы

Это исследовательское предложение, **не утверждённый контракт** и не реализация.
Сначала выбрать границу «изменение документа» / «бизнес-операция», затем отдельно
писать спецификации маленьких tools. Существующий XQuery остаётся escape hatch
со своими ранее описанными ограничениями.

## Варианты реализации

| Подход                                   | Плюсы                                                                                                                | Минусы / границы                                                                                                                                      |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. Типизированный patch через BS XML API | Использует фактически загруженную XMD, платформенные типы/defaults/OnBuild/hooks; не зависит напрямую от SQL dialect | Нужно корректно представить absent/default/arrays/IDs; не повторяет весь UI; save hooks могут иметь эффекты                                           |
| B. Raw XML import/replace через XML API  | Удобен для экспорта/миграций и сложных структур; маленький транспортный слой                                         | Риск потерять неизвестные/непоказанные поля; форма и XML не являются lossless storage round-trip; whole replace сложно контролировать                 |
| C. Отдельные бизнес-команды по типам     | Можно повторить нужные прикладные проверки, связанные документы, уведомления и права                                 | Требуется исследовать каждый тип и конфигурацию; нет универсальных параметров/rollback; версии поставки меняют поведение                              |
| D. Прямой SQL CRUD                       | Удобен для точной SQL-диагностики и специальных bulk migrations                                                      | Обходит объектный lifecycle и может рассинхронизировать XML/каталоги/кэши/индексы; схемы провайдеров различаются; не подходит как общий object editor |
| E. Прямой managed/.NET CRUD              | Потенциально удобная типизация/интеграция с существующей DLL                                                         | У нашей файловой DLL нет доказанного object API; обход BS не доказывает сохранение hooks/context/claims; callback bridge ранее имел отдельные сбои    |
| F. Автоматизация XMS UI                  | Ближе к конкретному интерактивному сценарию и его prompts                                                            | Требует UI/runtime context, хрупка, действия многодокументные; непригодна как основа простого серверного CRUD                                         |

Предпочтителен **A для документных операций + C для явно выбранных бизнес-команд**.
Raw XML можно оставить отдельным экспортным/административным сценарием позднее.
Вводить direct SQL/.NET mutations ради унификации с файловыми tools оснований
пока нет. Это не запрещает SQL существующего XQuery tool и не добавляет ему
read-only гарантий.

## Где выполнять работу

Платформенную работу с документами выполнять серверным BS XML API. Node/MCP
отвечает за строгий transport contract, bound limits, JSON schema, токены чтения
и классификацию результата. Если позже потребуется .NET для hashing/encoding,
это отдельный helper; он не должен незаметно заменить `Doc.Save` SQL-записью.

Discovery должен различать legacy/new model и основной/производный каталог.
Для неизвестного типа допустим явный полный form URL с подтверждённым назначением;
преобразование имени каталога в singular или путь `wtv_<name>.xmd` недостаточно.
Первая версия не обязана регистрировать типы, создавать каталоги или менять XMD.
Это самостоятельные schema migration operations.

## Кандидаты инструментов

| Возможность                 | Первый предлагаемый контракт                                                                      | Дополнительное исследование                                                       |
| --------------------------- | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Обнаружение типов/каталогов | Ограниченный inventory с источником, типом каталога и completeness flag                           | Реестр namespaced/custom компонентов и независимых projections                    |
| Описание схемы              | Структура, типы, кратность, defaults, foreign expressions, поля/методы раздельно, form provenance | Полнота inherited metadata, вычисляемые labels и custom template metadata         |
| Чтение объекта              | Identity + actual form + typed selected fields + snapshot token; массивы с pagination             | Sensitive fields, ext data, точные scalar encodings и стоимость                   |
| Создание                    | Указанный разрешённый тип, явные значения, платформенные defaults/hooks, возвращаемый ID строкой  | OnCreate/init effects, custom defaults, idempotency и duplicate checking          |
| Изменение                   | Последовательность явных операций по прочитанным путям; полный документ открывает сервер          | Compare-before-save, schemas changing, arrays и частично прочитанные данные       |
| Удаление                    | Отдельный trash-сценарий с известным типом и snapshot                                             | Binary resources, references, type-specific deletion и bulk limits                |
| Восстановление              | Отдельная операция по trash identity                                                              | Hooks при MoveDoc, collision с существующим ID, утраченные связи                  |
| Бизнес-команды              | Отдельные adapters и отдельная спецификация на каждый сценарий                                    | Участники событий, обучение, увольнение и т. п.; UI-equivalence не предполагается |

Имена и число tools пока не зафиксированы. Например, inventory+describe могут
быть одним tool, но operations `create`, `patch`, `trash`, `restore` полезно
разделить: у них разные preconditions, последствия и error recovery.
`delete_child` в XML-массиве не равно удалению объектного документа.

## Представление данных без потери смысла

Разделить scalar, structure, repeated element и reference. ID и integer больше
безопасного диапазона JSON Number возвращать decimal strings с типом; не
пытаться распознавать их по суффиксу имени. В legacy-модели integer-поле может
быть signed, reference — integer или string, а catalog row — вообще не объект.

Для поля нужны минимум type, hasValue и value. JSON null, empty string,
отсутствующий входной ключ, `clear` и применение default — различные действия.
Неизменённые поля не присылать обратно как новую полную структуру. TEMP,
PROPERTY/method, ID, doc_info и secondary data требуют отдельной writable policy;
не начинать с «всё, что есть в XMD, разрешено редактировать».

Путь patch задавать структурно, без `eval` и BS-expressions пользователя:
field segments, явный array selector/index, ожидаемый key/element fingerprint.
Если ключ встречается дважды, key-only update/delete возвращает неоднозначность.
Для массивов отдельно специфицировать append, update, remove, reorder и whole
replace. Замена целого массива требует чтения целого массива.

Foreign reference сохраняет ID и сведения об источнике, без автоматического
OpenDoc всех связанных объектов. При обещании проверки существования запрос
должен учитывать действительный foreign source; статический `common` enum и
объектный каталог не имеют одинакового lookup API.

## Чтение перед записью и конкуренция

Для object patch имеет смысл сохранить принцип существующих file tools:
агент должен прочитать изменяемые данные в текущей сессии, а tool проверяет,
что они не устарели. Для объектов предлагается отдельный token со scope:
connection/session, database+identity, actual form/schema fingerprint,
показанные field paths/array ranges и snapshot fingerprint.

Запрос XQuery по каталогу не означает чтение полного объекта. Чтение одной
страницы массива не даёт права whole replace всего массива. Токен из другой
сессии, другого объекта/схемы или после успешной записи не должен подходить.
Точные правила partial failure и расходования token требуют собственной spec.

Перед patch сервер повторно открывает **полный документ**, проверяет snapshot,
применяет изменения только к разрешённым путям, затем Save и проверенное чтение.
Так сохраняются остальные данные и обнаруживается известный stale snapshot.
Не использовать редактируемый cached/shared документ как рабочую копию.

**Такая проверка ещё не атомарный CAS.** Между проверкой и сохранением остаётся
окно гонки, если платформа не предоставляет надёжный lock/version/transaction.
Node mutex защищает только экземпляр нашего MCP; другой процесс, нода, агент
HCM или UI его не соблюдают. Native lost update показывает, что одного
`OpenDoc`/`Save` недостаточно. Нельзя объявлять strong concurrency guarantee
до отдельной проверки соответствующего платформенного механизма.

`doc_info.modification.date`, history/object_versions и `LastSavedData` не
доказаны как monotonic revision. Hash только показанных полей не обнаружит
изменений непоказанного массива, а hash всего XML может меняться из-за схемы
и сериализации. Выбор snapshot contract — отдельная маленькая задача.

## Валидация, preview и исполнение кода

XMD может выполнить код при загрузке/инициализации/создании, вычислении
свойств, сохранении и построении каталога. XMS запускает дополнительные действия.
Поэтому generic «dry-run делает всё, кроме Save» не гарантирует отсутствие
побочных эффектов. Не считать `SaveEvent(doc,false)` dry-run: в исследованных
исходниках он меняет связанные объекты и вызывает интеграции.

Первый preview можно определить лишь как структурную проверку запроса по
метаданным без выполнения save/business hooks. Он не гарантирует успешный
commit или отсутствие ошибок дальнейших проверок. Не показывать заранее
«итоговый точный diff», если неизвестно, что изменят hooks.

Не выключать save callbacks ради ускорения по умолчанию: они могут поддерживать
связи, нормализовать данные, ставить очереди и поднимать system events.
NOT-NULL/PRIMARY-KEY/FOREIGN-ARRAY не являются достаточными business validators.
Схема и прикладная конфигурация должны иметь разные provenance.

## Права и контекст

[Документация claims](https://wshcm-docs.boristype.dev/news/monolith/7158442922489027439.html)
прямо различает проверку top-level вызова и дальнейший server code: при запуске
разрешённого кода вложенные операции могут дополнительно не проверяться.
Следовательно, успешная authentication/evaluator initialization и
`HasWriteAccess=true` не доказывают соблюдение всех per-object/field permissions.

Необходимо отдельно определить, предоставляет MCP административную capability
учётной записи или обязан повторять UI authorization. Второе нельзя обещать
текущим evaluator без проверки low-privilege пользователя и trusted permission
API. Не выводить реальный доступ из XMS visible/required/control state.
Перед первой записью нужен конкретный spec этой границы, а не общий лозунг
«платформа сама всё проверяет».

## Результаты, ошибки и повторение

После исключения Save нельзя автоматически отвечать «ничего не изменено».
Возможны отказ до записи, сохранённый документ с ошибкой OnSave, частично
выполненные внешние действия, а также неизвестный исход при сетевом timeout.
HTTP timeout не отменяет серверный код.

В ответе операции нужны identity, фаза, достоверно установленный статус записи,
сведения о последующей проверке и новый snapshot только при его валидности.
Различать `not_started`, `failed_before_write`, `written`, `outcome_unknown`
можно только при достаточном evidence; не угадывать по тексту ошибки.
Ошибку последующего readback не выдавать за доказанный rollback.

Без доказанной идемпотентности не повторять create/save/delete/business call
автоматически. Возвращённый новый ID и request correlation полезны для
reconciliation, но сами не дают exactly-once. Best-effort undo не компенсирует
уведомление или вызов внешней системы. Первая версия может ограничиться
одним объектом и явным результатом каждого вызова; bulk atomicity не обещать.

## Предлагаемая последовательность маленьких задач

| Этап                                 | Результат                                                                  | Проверяемая граница завершения                                                                      |
| ------------------------------------ | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 0. Это исследование                  | Источники, пробелы, native probes                                          | 59 assertions, fixture cleanup, отсутствие новых object tools                                       |
| 1. Spec чтения и schema discovery    | Identity/scalar/schema contract и capability matrix                        | Cases для legacy/unknown/new model, custom/namespaced форм; никаких mutations                       |
| 2. Schema/read prototype             | Bounded reflection и чтение выбранных данных                               | Missing/default/large integer/array pagination/TEMP/PROPERTY/ext data; native + transport negatives |
| 3. Spec мутаций одного простого типа | Write policy, read tokens, errors, authorization boundary                  | Чётко описанные CAS limits и side effects; не неявный arbitrary type CRUD                           |
| 4. Create/patch для выбранного типа  | Маленькая измеримая вертикаль на `cost_center` либо ещё более простом типе | Stale/foreign/duplicate/schema-change/partial read/post-write error/timeouts + independent cleanup  |
| 5. Trash/restore                     | Отдельные tools без generic purge binary                                   | Native restore/collision/linked references; остатки проверяются независимо                          |
| 6. Один бизнес-adapter               | Один полезный прикладной сценарий с исследованным API                      | Побочные документы/уведомления/context известны и тестируются на собственных fixtures               |
| 7. Расширение матрицы                | Другие типы, Windows/MSSQL/new model/cluster                               | Acceptance на соответствующей среде, с явно указанными непроверенными вариантами                    |

Пока не исследованы все права/CAS/binary/transactions, это не причина блокировать
readonly шаг. Для мутаций эти пробелы нужно либо закрыть проверкой, либо явно
сохранить в ограниченном контракте. Финальный выбор подхода и scope первой записи
оставлен для следующего обсуждения; эта работа не начинает реализацию tools.
