# Намерение и порядок реорганизации документации BorisType

Дата намерения: 2026-11-10. Начало реализации: 2026-11-11.
Базовая ревизия обследования: `7a84cf0be1e7d338fef52d458938668719e565ce`;
ветка `docs/documentation-migration` создана от свежего `origin/main`
`8ff2739ce14957e9f1d3e3b17c7a7cf88a396209` (то же дерево после squash).

Статус: первый структурный срез подготовлен; дальнейшая содержательная ревизия остаётся открытой. Постоянные правила —
[refs/development.md](refs/development.md), текущая навигация — [refs/README.md](refs/README.md).
Переход не возобновляет приостановленные направления разработки и не является
новой технической аттестацией всех исторических утверждений.

## 1. Назначение этой записи

Зафиксировать намерение привести документацию к устройству проекта, который развивается
от компилятора TS → BS к инструментам взаимодействия с WebSoft HCM, MCP и C# библиотекам.
Сохранить полезный контекст компилятора и исследований платформы, сделать его доступным
следующему разработчику или агенту и сократить повторение старых ошибок.

Документ объединяет основания перехода, согласованные принципы, предварительную структуру,
план верхнего уровня и нерешённые вопросы. Это единственная рабочая запись данного перехода;
отдельные spec, plan, tasks и results для него сейчас не требуются.

Раздел 3 фиксирует договорённости. Конкретные пути в разделе 4 и решения, отмеченные как
предложения, ещё могут измениться. Перечень этапов не является разрешением автоматически
запускать пробы на HCM, менять реализацию инструментов или публиковать изменения.

Изначально эта запись фиксировала только намерение. После разрешения пользователя
начат перенос; таблица обследования ниже описывает исходное состояние, а не новые
известные дефекты документации. Ссылки направлены на сохранённые материалы либо
актуальные входы. Фактический охват текущего среза приведён в разделе 14.

## 2. Основания: что обнаружено

утверждений с кодом и проверка локальных ссылок. Это не построчная техническая аттестация
всех внутренних документов и не новый запуск compiler/MCP/.NET probes на целевой платформе.

## 3. Согласованные принципы

### 3.1. Две базы для разных задач

- `docs/` — пользовательская документация, публикуемая как сайт: что это такое,
  как подключить, куда обратиться, как пользоваться, какие возможности и ограничения есть.
  Здесь уместны и гайды, и справочник публичного API.
- `refs/` — внутренняя база разработчика и агента. Она помогает найти код и проверки,
  но в первую очередь отвечает на вопросы «на основании чего это сделано» и
  «почему выбрано именно это решение».

Пользовательский сценарий должен быть законченным без обязательного чтения старых планов.
Внутренняя запись должна позволять дойти от вывода до его основания и воспроизведения.
Сайт и внутренний справочник связываются ссылками там, где это полезно.

Развитие MCP и C# меняет приоритеты навигации, но не является основанием потерять
compiler cases, отрицательные результаты, ограничения или условия продолжения работ.
[Приостановка script/module](refs/decisions/2026-11-05-script-module-memory-freeze.md)
сохраняется; реорганизация документации не выбирает стратегию памяти.

### 3.2. Copilot/Cursor удаляются полностью

Удалить `.github/copilot-instructions.md`, три файла в `.github/instructions/`
и четыре файла в `.cursor/rules/`. Адаптеры для этих клиентов не сохраняются.
Это решение относится к инструкциям, а не к GitHub workflows или другим настройкам `.github/`.

Перед удалением проверить полезное содержание по текущему коду, выделить применимые
рабочие процедуры в skill или skills, сохранить обоснования во внутренней базе
и исправить входящие ссылки, включая ссылку из [AGENTS.md](AGENTS.md).
Не копировать старые инструкции в skill целиком и не создавать по skill на каждый старый файл.

`AGENTS.md` остаётся коротким входом: необходимые общие правила и маршруты к материалам
по задаче. Он не должен требовать чтения всех ADR, гайдов или исследований при каждом изменении.

### 3.3. Различаются факт, решение и долг

Внутренняя база должна явно различать:

- существующее поведение и устройство кода;
- наблюдение конкретного запуска и подтверждённую область применимости;
- принятое требование к новым изменениям;
- желаемое улучшение, которое ещё не реализовано;
- гипотезу или сообщение о проблеме, требующее проверки;
- историческое или заменённое решение.

Разумное требование не удаляется только потому, что старый код ему не соответствует.
Описываются причина требования, существующие отклонения и оставшаяся работа.
При этом намерение не выдаётся за уже реализованное свойство.

### 3.4. Суммаризация сохраняет основания

Сокращать материалы по техническим вопросам и решениям, объединяя сведения из разных
хронологических записей. В актуальном справочнике остаётся связное объяснение;
первичные результаты и полезные исторические материалы доступны по ссылкам.

Сохранять неудачные альтернативы, контрпримеры, ограничения, незакрытые вопросы
и причину выбора. «Короче» само по себе не является критерием качества.
Удаление дубля допустимо после проверки, что он не содержит уникальных полезных сведений.

### 3.5. Git и смысловая дельта дополняют друг друга

Git хранит точные изменения файлов. Для содержательного изменения описание PR фиксирует:

- было → стало: поведение, ограничение или утверждение;
- причину и существенные компромиссы;
- основание: проверки, пробы, результаты или источники;
- последствия для совместимости, установки и использования, когда они есть.

Различаются изменение реализации, исправление прежнего знания и расширение evidence.
Новый успешный запуск на Windows HCM расширяет подтверждение, но сам по себе
не означает изменения реализации. Исправление ошибочного описания Datex не доказывает
изменения платформы.

Актуальные документы обновляются по затронутому смыслу. Существенное изменение решения
или опровержение прежнего основания сохраняется в `refs/` со ссылками на предыдущую
запись и новые доказательства. Содержимое исторического запуска не переписывается
так, будто тогда проверялась новая версия.

Для мелкого изменения достаточно краткого описания. Отдельный `DELTA.md`, журнал
каждой заметки и обязательное обоснование опечатки не нужны. Changesets сохраняют
свою роль пользовательских release notes публикуемых пакетов.

### 3.6. Планы и задачи не образуют обязательную цепочку документов

Для небольшой задачи достаточно рабочего списка или checklist в issue/PR.
Для исследования можно вести одну заметку с вопросом, вариантами, результатами,
следующим шагом и критерием завершения, постепенно превращая её в итоговое обоснование.

Отдельный подробный план полезен для большой миграции с зависимыми этапами или передачи
работы исполнителю. Его назначение — оставшиеся действия и порядок выполнения.
После завершения актуальное объяснение переносится в справочник; план сохраняется
как история, если у него есть самостоятельная ценность.

Цепочка `spec → plan → tasks → results` не требуется для каждой фичи. Файл плана
не должен оставаться единственным источником действующего контракта.

### 3.7. TODO хранит конкретный долг

Предлагаемое распределение ролей принято как направление:

- `TODO.md` — конкретные отклонения, известные проблемы и оставшиеся проверки;
- `refs/` — основания решений и описание текущего состояния;
- `ROADMAP.md`, если сохраняется, — направления и крупные ограничения;
- issue — подробная работа над выделенной задачей; в TODO остаётся ссылка вместо
  второй копии описания и статуса.

При разборе старых пунктов отличать подтверждённый дефект, предложение улучшения
и непроверенное подозрение. Проверять, не выполнена ли задача и не устарело ли её основание.
В первом срезе принят короткий ROADMAP направлений и отдельный TODO конкретного долга.
Исходные списки сохранены в архиве; непроверенные старые находки выделены явно.

## 4. Организация материалов

Согласовано имя внутренней базы **`refs/`**. Существующие опубликованные маршруты
`docs/guides/` и `docs/reference/` сохранены; тематическая навигация не требует
переноса всех пользовательских URL.

```text
README.md                 Обзор направлений и входы
AGENTS.md                 Короткие общие правила и маршруты
TODO.md                   Конкретный долг и ссылки на issues
ROADMAP.md                Направления без дублирования статусов
DOCUMENTATION_TRANSITION.md Временная запись текущей миграции
docs/                     Пользовательский сайт: guides/, reference/
refs/                     Внутренняя база
  README.md               Карта тем, кода и проверок
  development.md          Ведение баз, проверки и дельта
  mcp/, dotnet/            Устройство, ABI, причины границ
  compiler/, platform/    Карта реализации и общие знания HCM
  decisions/              Сохранённые значимые решения
  research/               Исследования вместе с пробами и результатами
  archive/                Историческая архитектура, ревью и планы
  migration-map.json      Соответствие исходных материалов и hashes
skills/                   Самодостаточные устанавливаемые пользовательские skills
.agents/skills/            Узкие checkout-local процедуры разработчика
```

Тематическая навигация предпочтительнее поиска только по типу документа или номеру этапа.
Общие сведения о HCM не должны обнаруживаться исключительно через историю MCP.
Внутри темы дополнительные уровни появляются при необходимости, а не по шаблону.

README пакета даёт назначение, быстрый старт и доступ к подробностям. При сокращении
учитывается отдельная публикация npm/ZIP: ссылки из установленного пакета должны
оставаться полезными без полного checkout.

Устанавливаемые пользовательские skills остаются самодостаточными и выборочными.
Внутренний skill разработки может требовать checkout и читать его `refs/`, если это
явно обозначено. Compiler workflow находится в `.agents/skills/boristype-compiler-development/`;
он обнаруживается через AGENTS и compiler entry.
Существующие локальные неотслеживаемые материалы `.agents/` не включаются в перенос автоматически.

## 5. Как готовить внутренние записи и сокращать старые

### 5.1. Полезное содержание записи

Для существенного технического вопроса нужно иметь возможность найти проблему,
выбранное решение, причины и альтернативы, последствия, основания, область применимости
и условия пересмотра. Это критерий содержания, а не обязательный набор заголовков.
Отдельная ADR нужна для значимого решения; обычное уточнение может оставаться разделом темы.

Карта кода указывает ключевые точки входа и проверки. Полное перечисление файлов
и пересказ очевидных сигнатур быстро устаревают и не заменяют обоснования.
Имена, полезные для поиска, стоит сохранять рядом с понятным описанием по-русски.

### 5.2. Порядок разбора группы старых материалов

1. Собрать относящиеся к вопросу записи и ссылки на реализацию/проверки.
2. Разделить текущие сведения, исторические наблюдения, предложения, опровергнутые
   утверждения и незавершённую работу.
3. Проверить спорное и существенное по доступным источникам; отсутствие возможности
   проверки обозначить явно.
4. Написать актуальное объяснение с причиной выбора и ссылками на evidence.
5. Уникальные открытые проблемы направить в TODO/issue, сохранив их основания.
6. Для каждого исходного материала выбрать: сохранить, объединить, архивировать
   или удалить после извлечения полезного. Зафиксировать соответствие старого и нового места.
7. Проверить ссылки, комплектность evidence и возможность найти материал по теме.

Старое ошибочное утверждение не обязано оставаться в актуальном тексте, но исправление
значимого вывода должно быть прослеживаемым. При удалении исходника ссылка на него
заменяется доступным основанием или ссылкой на конкретную историческую ревизию.
Git не должен быть единственным способом узнать, почему очевидный подход не подходит.

### 5.3. Примеры сведений, которые нельзя потерять при сокращении

- **BS → C# boundary.** Поиск выполняется самостоятельной DLL, URL разрешается в BS.
  Обратный Datex callback приводил к падению исследованного C-runtime; причина
  не установлена. Это основание текущего выбора, а не доказательство невозможности
  любых callbacks на всех версиях. См. [решение](refs/decisions/2026-11-06-dotnet-search-boundary.md)
  и [эксперимент](refs/research/mcp/06-dotnet-probe.md).
- **Compound for-update.** Наблюдалось зависание; выбранный IR-обход прошёл ручной
  C smoke. Успех обхода не доказывает внутреннюю причину дефекта парсера.
  См. [решение](refs/decisions/2026-10-07-safe-for-updates.md) и [результаты](refs/research/compiler-control-flow/probes/README.md).
- **Expression baseline.** В checkpoint от 2026-11-05 зафиксированы 10 PASS и
  38 exact XFAIL из 48 comparisons. Зелёный baseline означает воспроизводимость
  известных дефектов, а не исправленную семантику. См. [checkpoint](refs/research/compiler-semantics/results/2026-11-05-research-checkpoint.md).
- **Файлы и blobs.** Физическая файловая операция и чтение логического URL могут
  обращаться к разным данным. Это влияет на выбор tools и проверку результата.
  См. [исследование routing](refs/research/dotnet/15-url-storage-routing-research.md).

Эти результаты здесь пересказываются по существующим материалам; новых native запусков
при подготовке переходной записи не было.

## 6. Evidence, пробы и границы воспроизводимости

Документация Datex может пропускать аргументы и содержать ошибочные описания.
Сохраняются правила из [AGENTS.md](AGENTS.md): конкретные ссылки на документацию,
сверка подходящих сигнатур с [wshcmx/types](https://github.com/wshcmx/types) с revision/файлом
и различение документации, declarations, кода поставки, JS/mock и C-runtime evidence.

Для результата пробы важны исходник, способ запуска, actual/expected, версия среды,
ОС, runtime и место выполнения, проверяемая ревизия или идентичность артефактов,
ограничения запуска и результат очистки. Неизвестное обозначается как неизвестное;
наличие SHA256 не заменяет доступность исходных предпосылок.

Managed tests на Windows не доказывают загрузку DLL в Windows HCM. JS result
не подтверждает C semantics. Выполнение bare output не аттестует script/module.
Результат старого запуска не приписывается новому output без соответствующего основания.

В `plans/` находятся не только Markdown, но и собственные BS-пробы, manifests,
очищенные результаты и verifier-скрипты. Такие группы переносятся комплектами;
проверяются относительные пути, hashes и команды воспроизведения.
Исторические артефакты не переформатируются попутно с документацией.

Регрессионные тесты и генераторы, уже принадлежащие пакету, могут оставаться рядом
с кодом. Внутренняя база ведёт к ним; переносить исполняемые источники в `refs/`
только ради симметрии дерева не требуется.

Известные crash/hang probes должны отличаться от обычных проверок. Чтение записи
не запускает её автоматически; timeout клиента не доказывает прекращения серверного кода.
Повторное выполнение таких экспериментов не входит в механическую миграцию документов.

`refs/` находится в публичном репозитории. Сохраняются собственные исходники, допустимые
очищенные результаты и ссылки/идентификаторы источников. Vendor runtime, полные закрытые
материалы, учётные данные и приватные данные стенда не переносятся в git.
Если для воспроизведения нужен отдельно предоставленный runtime, это указывается явно.

Отдельно проверяется обнаружение и работа skill после удаления старых инструкций:
само наличие файла `SKILL.md` не доказывает, что другой агент найдёт и применит его.

## 8. Пример технического долга: завершение процесса из core

Текущее состояние подтверждено чтением кода: вызовы `process.exit()` есть в
[config.ts](packages/bt-cli/src/core/config.ts),
[linking/index.ts](packages/bt-cli/src/core/linking/index.ts) и
[linking/parsers.ts](packages/bt-cli/src/core/linking/parsers.ts), включая успешный exit.

Направление: core возвращает результат или передаёт ошибку вызывающему коду;
CLI управляет завершением процесса и exit code. Причина — возможность переиспользования
core и управления cleanup вызывающей стороной.

При переносе в TODO следует сохранить проблему, основание и желаемый результат.
Критерий завершения: core возвращает управление при успехе и ошибке, CLI сохраняет
ожидаемые exit codes, очистка ресурсов выполняется. Конкретный способ передачи ошибок
и объём миграции выбираются при работе над задачей.

Для нового core-кода направление применимо сразу; старые нарушения остаются явным долгом.
Реорганизация документации не включает автоматическое исправление этих вызовов.

## 12. Как оценивать результат

Для выбранного среза перехода должны выполняться следующие условия:

- Из корневого README понятны направления проекта и входы для пользователя/разработчика.
- Из AGENTS и внутреннего оглавления можно найти материал по задаче без чтения всего корпуса.
- У текущего технического вывода доступны причина, основание и границы применимости.
- Старые инструкции Copilot/Cursor удалены после извлечения полезного; входящие ссылки исправлены.
- Для перенесённых, объединённых, архивированных и удалённых материалов есть соответствие
  исходному корпусу; уникальные полезные сведения и открытые проблемы учтены.
- Сохранены compiler checkpoints, известные расхождения и условия возобновления script/module.
- Пробы и evidence не потеряны, prerequisites и ограничения воспроизведения понятны.
- Пользовательские инструкции согласованы с текущими контрактами соответствующего среза.
- Проверены затронутые ссылки, навигация и сборка сайта; исключения перечислены отдельно.
- Skills можно найти и применить в предусмотренной среде, без случайной зависимости
  пользовательского skill от локального checkout.

Практические маршруты для проверки навигации:

1. Найти причину отказа от Datex callbacks и исходный эксперимент с границами вывода.
2. Найти compiler counterexample, способ генерации/запуска и смысл PASS/XFAIL результата.
3. Понять, где добавлять MCP tool и какие локальные/native проверки относятся к нему.
4. Установить совместимую DLL по пользовательской документации и проверить её API.
5. Найти оставшийся долг по `process.exit()` и отличить его от текущего устройства core.

Эти маршруты проверяют достижимость знаний; они не означают автоматического запуска
описанных native действий в рамках проверки документации.

Полная compiler/MCP/.NET acceptance не заявляется только по результатам сборки сайта
или проверки ссылок. Для изменений лишь Markdown достаточно относящихся к ним проверок;
изменение исполняемых snippets, probes, skills scripts или упаковки требует своих проверок.

- `docs:check` проверяет локальные файловые цели Markdown и VitePress navigation,
  coverage карты переноса и hashes evidence; `docs:test` проверяет сам checker на
  положительных и отрицательных fixtures. Нужна доступная baseline git history
  (CI использует полный checkout). Проверка не обращается к внешним URL, не
  аттестует смысл текста и не проверяет все anchors.

Отложено: построчная техническая ревизия исторических документов, повторение native
проб, подтверждение всех старых findings и дальнейшее удаление/сжатие архива.
Непереносимые абсолютные ссылки на локальный vendor source превращены в текстовые
locators; они требуют отдельно предоставленного runtime. Оставшиеся исторические
неразрешённые цели учитываются поштучно в `refs/link-exceptions.json`.
Открытые задачи не скрываются архивом — см. TODO.

Проверки среза:

- `docs:test`: 12/12 положительных/отрицательных fixtures; проверяются missing targets,
  navigation, Markdown со вложенными скобками, directory/index и public assets,
  потерянная запись карты и изменение evidence bytes.
- `docs:check`: локальные файловые цели и main GitHub links этого репозитория,
  156 записей карты, 30 byte-preserved artifacts; три известных исторических link gaps.
- `docs:build` и `format:check`; warning VitePress о подсветке `gitignore` не влияет
  на рендеринг и не относится к платформе.
- Сохранённые object-model verifiers: 59/59 и 53/53 recorded observations,
  transcript hashes и cleanup receipts; это локальная проверка сохранённых данных.
- Compiler skill прошёл structural validator и независимый read-only сценарий
  применения. Три маршрута чтения (compiler, DLL boundary/evidence, установка DLL)
  достигли нужных источников. Два найденных навигационных пробела исправлены:
  прямая .NET build ссылка и явный bare expression regression рецепт.
- Для всех 30 artifact paths `.gitattributes` отключает Git EOL conversion,
  чтобы Windows checkout не менял исторические bytes.

Полная проверка внешних URL и всех anchors, техническая ревизия всех старых
утверждений и новая compiler/MCP/.NET runtime acceptance в этот срез не входят.
Изменения реализации ограничены checker/CI для документации; в runtime/compiler
изменены только комментарии с путями. Native пробы на стенде не выполнялись.
